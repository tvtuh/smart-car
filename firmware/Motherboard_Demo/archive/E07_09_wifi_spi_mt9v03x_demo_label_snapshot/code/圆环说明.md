# 圆环（环岛）识别说明

参考文章：[智能车图像处理(三)元素判断](https://blog.csdn.net/weixin_50567482/article/details/119406477)

## 一、先说清楚：文章里圆环部分没有代码

这篇文章里**只有三岔路口给了完整代码**，圆环（和车库）都只有文字描述。
文章对圆环给了两套方法：

**方法一：通过寻找拐点判断**

1. 判断**对面那条边界**为连续直道
2. 找到入口一侧的**下拐点** → 状态一
3. if(状态一) 找**中拐点** → 状态二
4. if(状态二) 找**上拐点** → 状态三（进环）
5. 出环时找另一侧的下拐点
6. 赛道宽度变宽，丢线数目大于阈值

**方法二：通过判断赛道黑白跳变点**

1. 判断对面那条边界为连续直道
2. 固定两行判断，在入口下拐点的上方为**全白**；
   继续往下隔 3 行扫描，共扫 4 行，看这几行同一行是否存在
   **由白到黑以及黑到白的跳变点**，只要有一行存在即可置为状态一
3. 找 5 行判断，当入口那一侧边界的列数大于一阈值，置为状态二
4. 判断另一侧的**黑色块个数**，随着车偏移 多 → 少 → 多
5. 出环时，判断左右两边白色个数及赛道宽度

所以 `code/ring_road.c` 是**按这两段文字描述实现**的，不是抄文章的代码。

## 二、本实现

**两套方法的特征都用上，互相印证**：

| 判据 | 对应文章 | 实现 |
| --- | --- | --- |
| 对面是连续直道 | 方法一/二的第 1 条 | `ring_is_straight()`：先看丢线行数，再最小二乘拟合看最大偏差 |
| 入口侧有向外张开的拐点 | 方法一第 2 条 | `ring_find_corner()`：边界在几行内突然向外张开 |
| 全白行 | 方法二第 2 条 | `ring_scan_feature_rows()`：扫图像上半部分找白点最多的行 |
| 黑白跳变行 | 方法二第 2 条 | 同一函数里统计每行的黑白交界次数 |

**识别条件 = 对面直道 且 有拐点 且 （有全白行 或 有跳变行）**

左右环完全对称，靠 `to_left` 参数区分；左环看左边界、右环看右边界。

**状态机**（对应文章的"状态一/二/三/出环"）：

| 状态 | 含义 | 推进条件 |
| --- | --- | --- |
| 0 | 不在圆环 | 识别条件成立（连续 `RING_CONFIRM_FRAME` 帧） |
| 1 | 识别到入口 | 入口侧丢线 ≥ `RING_IN_LOST_MIN`（道路张开了） |
| 2 | 正在进环 | 出现环内特征（全白行或跳变行） |
| 3 | 环内 | 入口侧丢线 ≤ `RING_OUT_LOST_MAX` |
| 4 | 正在出环 | 两侧丢线都恢复 → 回到状态 0 |

## 三、上车实测暴露的问题与修正

第一次把车放在圆环入口，示波器读数：

| 通道 | 值 | 含义 |
| --- | --- | --- |
| ch0 左丢线 | **0** | 左边线一行都没丢 |
| ch1 右丢线 | **56** | 右边线丢了 56 行（道路向右张开了） |
| ch3 十字状态 | **1** | ❌ 十字被误报了 |
| ch4 圆环 | **0** | ❌ 圆环没识别出来 |

### 问题 1：圆环没识别出来

原来用的是"**拐点突变**"判据（文章方法一），但那 20 多像素的突变**正好落在丢线行上**，
存进数组的是"保持上一行"的值，突变在数组里根本看不到。

**改法**：主判据换成更直接的形式（拐点判据保留为备用）：

| 条件 | 内容 | 实车数据 |
| --- | --- | --- |
| 1 | 对面那条边线是连续直道（丢线 ≤ 2 行且接近直线） | 左丢线 0 ✓ |
| 2 | 入口这一侧有**一段足够长的连续丢线**（≥ 25 行） | 右丢线 56 ✓ |
| 3 | **这段行范围里对面基本不丢线**（≤ 3 行） | 左丢线 0 ✓ |

**条件 3 是区分圆环和十字的关键**：十字的横杠会把左右两侧**同时**盖住，
圆环入口只有一侧道路张开、另一侧还是直道。

仿真验证（各 8 组）：

| 场景 | 报左环 | 报右环 | 未报 |
| --- | --- | --- | --- |
| 直道 | 0/8 | 0/8 | 8/8 |
| 弯道 | 0/8 | 0/8 | 8/8 |
| 正入十字 | 0/8 | 0/8 | 8/8 |
| 斜入十字 | 0/8 | 0/8 | 8/8 |
| **右侧张开（右环入口）** | 0/8 | **7/8** | 1/8 |
| **左侧张开（左环入口）** | **8/8** | 0/8 | 0/8 |

### 问题 2：十字被误报

圆环入口的丢线是"左 0 / 右 56"，而十字的条件 1 只要求"两侧之和够多 + 至少一侧够多"，
56 满足 → 十字就此误报。

**改法**：给十字加一条 —— **左右两侧必须有多少行是"同时丢"的**（`CROSS_OVERLAP_MIN = 3`）。

| 场景 | 左丢线 | 右丢线 | **同时丢的行数** |
| --- | --- | --- | --- |
| 正入十字 | 40 | 39 | **39** |
| 斜入十字(0.12) | 36 | 41 | **29** |
| 斜入十字(0.20) | 26 | 31 | **3.6** |
| **右环入口** | **0** | **56** | **0** ← 排除 |
| 直道/弯道 | 0 | 0 | 0 |

### 问题 3：右环识别成功，左环还是不行

左右环各测一次之后：

| 场景 | ch0 左丢线 | ch1 右丢线 | ch3 十字 | ch4 圆环 |
| --- | --- | --- | --- | --- |
| 右环入口 | 0 | 50 | 0 ✓ | **23**（右环，状态3）✓ |
| 左环入口 | 47 | **8** | 0 ✓ | **0** ✗ |

左环失败的原因：对面（右边）丢了 **8 行**，而"对面是连续直道"这条判据当时要求 **丢线 ≤ 2 行**，
8 > 2 直接被否掉了。

**改法**：放宽 + 增加一条更干净的区分条件。

| 参数 | 原来 | 现在 | 原因 |
| --- | --- | --- | --- |
| `RING_STRAIGHT_LOST_MAX` | 2 | **10** | 实车左环对面丢 8 行；直线度由偏差阈值保证 |
| `RING_OPPO_LOST_MAX` | 3 | **8** | 同上 |
| `RING_OPPO_RUN_MAX`（新增） | — | **15** | **对面那条边线自己也不允许有太长的连续丢线段** |

`RING_OPPO_RUN_MAX` 这一条是为了补上放宽带来的副作用：
**极端斜入十字**（横杠特别斜）时，左右两边的丢线段是"接着"的（一个在上一个在下），
只靠"范围重叠"区分不开，放宽后误报率升到 4/8；加上这一条之后回到 **0/8**。

放宽后的完整回归测试（各 8 组）：

| 场景 | 报左环 | 报右环 | 未报 |
| --- | --- | --- | --- |
| 直道 | 0/8 | 0/8 | 8/8 |
| 弯道 | 0/8 | 0/8 | 8/8 |
| 正入十字 | 0/8 | 0/8 | 8/8 |
| 斜入十字(0.12) | 0/8 | 0/8 | 8/8 |
| **斜入十字(0.20，极端)** | **0/8** | **0/8** | 8/8 |
| 右环入口 | 0/8 | **7/8** | 1/8 |
| 左环入口 | **8/8** | 0/8 | 0/8 |

### 失败原因诊断（ch4 的负数）

没识别到圆环时，ch4 会给出**是哪一条判据没过**：

| ch4 | 含义 |
| --- | --- |
| 0 | 没跑 / 没到判断这一步 |
| **-1** | 对面那条边线不算"连续直道" |
| **-2** | 入口侧道路没张开（既没有长丢线段也没有拐点） |
| **-3** | 对面在张开段也丢线，或者对面自己也有长丢线段（更像十字） |

### 问题 4：左环仍然不行，但诊断指明了方向

再测一次左环，`ch4 = -1`（对面那条边线不算"连续直道"），ch0 = 47 / ch1 = 8。

"对面直道"这个判据里有 4 个子条件，光看 -1 不知道是哪一个。所以这次做了两件事：

**1. 把失败原因拆细**

| ch4 | 含义 |
| --- | --- |
| -11 | 对面丢线太多（> `RING_STRAIGHT_LOST_MAX`） |
| -12 | 对面有效点太少（< `RING_STRAIGHT_MIN_PT`） |
| -13 | 拟合退化 |
| **-14** | **对面不够直（拟合偏差 > `RING_STRAIGHT_DEV_MAX`）** |

**2. 没识别到时 ch5/ch6 改报实测数值**

| 通道 | 识别到时 | 没识别到时 |
| --- | --- | --- |
| ch5 | 入口拐点所在行 | **对面边线的拟合偏差（像素）** |
| ch6 | 入口拐点所在列 | **对面边线的丢线行数** |

**3. 放宽偏差阈值**

`RING_STRAIGHT_DEV_MAX`：**6.0 → 12.0**。

实车对面（右边）边线肉眼看是直的，但边界数组本身有一两个像素的量化抖动，
再加上丢线行"保持上一行值"造成的台阶，6 像素太严会被误判成"不够直"。

回归测试：放宽后直道 / 小弯 / 中弯 / 大弯**仍然 0/8 误报**，右环入口仍是 7/8。

### 问题 5：诊断本身有 bug（ch4=-14 但 ch5=1，自相矛盾）

左右环各测一次的读数：

| 场景 | ch4 圆环 | ch5 | ch6 |
| --- | --- | --- | --- |
| 右环 | **23** ✓ | 47 | 155 |
| 左环 | **-14**（对面不够直） | **1** | 7 |

`-14` 表示"拟合偏差超过了 `RING_STRAIGHT_DEV_MAX`（当时是 12）"，
但 ch5 报出来的偏差却只有 **1 像素** —— 自相矛盾。

**原因**：状态机会先试"丢线多的一侧"（左环时先试左侧），失败后再试另一侧；
第二次尝试又把 `ring_dbg_dev` / `ring_dbg_lost` 覆盖了一遍，
所以示波器上看到的是**第二次尝试**（对面是左边线，本来就直）的数值，
真正失败的那次（对面是右边线）的数值被冲掉了。

**修法**：

1. 主尝试（丢线多那一侧）的实测值单独存一份（`ring_rep_dev` / `ring_rep_lost`），不再被覆盖
2. `ring_straight_fail` 每次重新判之前清零，避免残留上一次的结果
3. `RING_STRAIGHT_DEV_MAX`：**12 → 20**

现在没识别到时：**ch4 = 失败原因，ch5 = 主尝试测到的拟合偏差，ch6 = 主尝试测到的对面丢线行数**，
三个数是同一次尝试的，可以直接对应起来定阈值。

### 问题 6：直线度用"最大偏差"太脆弱 → 改成"中位数偏差"

修好诊断之后再测，数据对上了：

| 场景 | ch4 | **ch5 拟合偏差** | ch6 对面丢线 |
| --- | --- | --- | --- |
| 右环入口 | -14 | **58** | 4 |
| 左环入口 | -14 | **44** | 4 |

ch5 是 44~58 像素 —— **但对面那条边线肉眼看是直的**。

原因：边界数组里**偶尔有几行是离群点**（种子行的初始误差、个别行的跳变），
用"最大偏差"衡量直线度会被这几行**直接拉爆**；而绝大多数行其实几乎完美贴合直线。

**改法**：直线度改用**偏差的中位数**衡量（直方图法，不用排序，很便宜）。

PC 仿真对比（直道 / 右环对面 应该判"直"，弯道应该判"不直"）：

| 场景 | 最大偏差 | **中位数偏差** |
| --- | --- | --- |
| 直道 | 7.1 | **1.5** |
| 右环入口对面 | 7.5 | **2.2** |
| 小弯 | 7.2 | 1.5 |
| 中弯 | 6.4 | 1.2 |

`RING_STRAIGHT_DEV_MAX` 的含义随之改为**中位数上限**，取值 **6**（原来是最值，取 20）。

> 中位数对"少数离群行"天然免疫 —— 只要一半以上的行贴合直线就判为直，
> 这正是我们想要的语义。

## 五、圆环补线（`ring_fix_line`）

### 第一版是错的：把边界推到了图像边缘

第一版的做法是"从入口拐点往上、按固定斜率把圆环侧边界朝环内推"。实车一看就出问题了：

**补出来的边界一路顶到图像最右边（第 187 列）**。这样
`中线 = (左边界 + 187) / 2` 会比实际中线**偏向环外侧约 30 像素** → 车往环外冲。

根因：**补线没有约束**。斜率乘上行数，推多少完全没上限，推着推着就出画面了。

### 现在的做法：相对"对面那条可靠的边线"来补

关键思路：**补出来的边界 = 对面那条边线 + 赛道宽度（+ 入环偏移）**。

| 步骤 | 做法 |
| --- | --- |
| 1. 量宽度 | 用**拐点以下**那一段（也就是正常的直道）里两条边线都有效的行，统计出赛道的真实宽度 |
| 2. 逐行补 | 圆环侧边界 = 对面边界 ± 赛道宽度 ± 入环偏移 |

这样补出来的边界**永远在赛道附近**，不可能像第一版那样跑到画面外面去。

| 状态 | 入环偏移 | 效果 |
| --- | --- | --- |
| 入环（1/2） | 从 0 线性加到 `RING_IN_BIAS_MAX` | 中线朝环内最多偏 15 像素，**平滑、有上限** |
| 环内（3） | — | **不补**（环内白区就是环的路面） |
| 出环（4） | **0** | 边界与对面那条直道平行 → **车直着出去** |

数值验证（赛道宽 90 像素，拐点在第 56 行）：

```
=== 右环 入环：补右线后中线的偏移 ===
row= 12   中线偏移 +11      row= 36   偏移 +5
row= 24   中线偏移  +8      row= 60(拐点) 偏移 0
=== 右环 出环：中线偏移全部为 0（直着走）===
对比：第一版会把右线推到 187，中线偏移 +30 像素 ← 车就冲出去了
```

### 第三版：宽度按行算（前视梯形）+ 出画面就不补

**实车现象（直道上，示波器 ch4 = 11 = 左环/状态1，ch5 = 92 = 入口拐点在第 92 行）**：
左边线突然"断成两截"——第 91 行还是 30，第 88 行直接跳到 **0**，往上 5~88 行全是贴着画面左边的 0；
中线跟着整段右移。**过大约 10 秒自己又好了**。

从那张截图里量出来的数据（右边线是好的，只有左边线被改写）：

| 行 | 右边界（正常） | 左边界（实测） |
| --- | --- | --- |
| 119 | 166 | 16 ✓ 正常 |
| 95 | 154 | 27 ✓ 正常 |
| 91 | 153 | 30 ✓ 正常（拐点） |
| 88 | 151 | **0** ← 从这里开始被补线改写 |
| 71 | 143 | **0** |
| 23 | 118 | **0** |

**根因 1：拿"近处的平均宽度"去补"远处的行"。**
摄像头是前视的，赛道在图像里是**梯形**：近处（行号大）宽、远处（行号小）窄。
拐点以下（第 92~119 行）量出来的平均宽度是 **137** 像素，而第 23 行那儿的真实宽度只有 **80** 左右。
于是 `左线 = 右线 − 137 − 偏移 = 118 − 137 − 30 < 0` → 被限幅到 **0**，整段贴到了画面左边。
（这就是第一版那个"推到画面边缘"的老毛病，换了个形式又回来了。）

**根因 2：误判进状态 1 之后出不来。**
状态 1 的出口是"那一侧道路张开（大量丢线）"。直道上根本不会张开，
而当时 `ch0 = 0`（左线一行都没丢），所以只能等 `RING_STATE_TIMEOUT = 200 帧 ≈ 10 秒`。

**改法（三条）**：

| 改动 | 做法 | 效果 |
| --- | --- | --- |
| ① 宽度按行算 | 对"宽度 vs 行号"做一次**线性拟合**（斜率限幅 `RING_WIDTH_SLOPE_MAX = 2.0` 像素/行），逐行算宽度，并兜在 `[w拐点/2, w拐点×1.5]` 内 | 补出来的线跟着梯形走，不再把远处的行推出去 |
| ② 出画面就不补 | 算出来的值如果 `< 0` 或 `> 187`，**这一行跳过**，保持寻线原来的结果 | 宁可这一段不补，也绝不允许把边线贴到画面上（贴上去会把中线整个带偏） |
| ③ 状态 1 短耐心 | `RING_FIND_FAIL_MAX = 60`：连续 60 帧等不到"张开"就复位重新识别 | 假入口约 3 秒就自己消失，不再挂 10 秒 |

同一帧用新公式重算（右边界不变）：

| 行 | 旧：右−137−偏移 | 新：右−宽度(行)−偏移 |
| --- | --- | --- |
| 88 | 151−137−2 = **12** | 151−120−2 = **29** |
| 71 | 143−137−10 = **−4 → 0** | 143−104−10 = **29** |
| 23 | 118−137−30 = **−49 → 0** | 118−62(兜底)−30 = **26** |

（用整幅图的梯形外推估计，第 71 行的真实左边线约 28 像素 —— 新公式给 29 ✓）

### 两个调节旋钮

| 宏 | 默认 | 说明 |
| --- | --- | --- |
| `RING_IN_SLOPE` | 0.5 | 入环时中线朝环内偏的速率，**调大 = 更早更猛地往环里拐** |
| `RING_IN_BIAS_MAX` | 30 | 入环偏移的**上限**（像素）。这个上限是必须的，第一版没有它才出的事 |

### 调试开关

`RING_FIX_ENABLE = 0` 可以**只识别不补线**，用来对比"补了 / 没补"的差别。

## 六、PC 仿真验证（合成圆环）

合成的圆环图（188×120，主赛道 + 白色圆环带、环内是黑色岛），8 组随机测试：

| 场景 | 报左环 | 报右环 | 未报 |
| --- | --- | --- | --- |
| 直道（不该报） | 0/8 | 0/8 | 8/8 |
| 弯道（不该报） | 0/8 | 0/8 | 8/8 |
| **左圆环** | **8/8** | 0/8 | 0/8 |
| **右圆环** | 0/8 | **8/8** | 0/8 |
| **较远的左圆环** | **8/8** | 0/8 | 0/8 |

左右不会混淆，直道弯道零误报。

### 仿真中发现的一个坑

入口那个突变（20 多像素）**经常正好落在丢线行上** —— 因为种子生长法在小范围内找不到这么大的跳变，
就把那几行标记成丢线了。如果按文章三岔代码那样要求"连续 4 行不丢线"，**拐点会被整段漏掉**
（第一版就是这么失败的，识别率 0/8）。

改成**比较相邻两个有效行（可以跨过丢线行）**之后，识别率 0/8 → 8/8。

## 四、参数（`code/ring_road.h`）

### 对面直道判断

| 宏 | 默认值 | 说明 |
| --- | --- | --- |
| `RING_STRAIGHT_Y1/Y2` | 72 / 119 | 取行范围（靠近车身那一段） |
| `RING_STRAIGHT_LOST_MAX` | 2 | 这段里对面边线最多丢几行 |
| `RING_STRAIGHT_DEV_MAX` | 6.0 | 拟合直线后的最大偏差（像素），越小越"直" |

### 入口侧"道路张开"（和十字的关键区别）

| 宏 | 默认值 | 说明 |
| --- | --- | --- |
| `RING_OPEN_LOST_MIN` | 25 | 入口侧最长连续丢线段至少多少行 |
| `RING_OPPO_LOST_MAX` | 3 | 这段行范围里，对面最多允许丢几行 |

### 入口拐点（备用判据）

| 宏 | 默认值 | 说明 |
| --- | --- | --- |
| `RING_SCAN_NEAR/FAR` | 114 / 30 | 拐点扫描的行范围 |
| `RING_JUMP` | 8 | 相邻有效行边界突变多少像素算拐点 |
| `RING_JUMP_ROWS` | 6 | 两个有效行最多隔多少行还能比较 |

### 全白行 / 跳变行

| 宏 | 默认值 | 说明 |
| --- | --- | --- |
| `RING_WHITE_MIN` | 170 | 一行里白点超过本值算全白行（共 188 点） |
| `RING_TRANS_MIN` | 2 | 一行里黑白跳变次数达到本值算跳变行 |
| `RING_FEATURE_ROW1/2` | 20 / 72 | 在这段行里找全白行/跳变行 |

### 状态切换

| 宏 | 默认值 | 说明 |
| --- | --- | --- |
| `RING_IN_LOST_MIN` | 35 | 入口侧丢线超过本值 → 判定已经进环 |
| `RING_OUT_LOST_MAX` | 12 | 入口侧丢线少于本值 → 判定已经出环 |
| `RING_STATE_TIMEOUT` | 200 | 状态保护，防止卡死 |
| `RING_CONFIRM_FRAME` | 2 | 连续几帧满足条件才确认 |

## 五、示波器怎么看

| 通道 | 内容 |
| --- | --- |
| ch4 | **圆环 类型×10 + 状态** —— 0 = 没有圆环；11/12/13/14 = 左环状态 1~4；21/22/23/24 = 右环状态 1~4 |
| ch5 | 圆环入口拐点所在行 |
| ch6 | 圆环入口拐点所在列 |

过圆环时 ch4 应该走 **11 → 12 → 13 → 14 → 0**（左环）或 **21 → 22 → 23 → 24 → 0**（右环）。

## 六、上车调参建议

1. **先只调识别**：把车放在圆环入口前，看 ch4 有没有跳到 11 或 21。
   - 不跳 → 大概率是 `RING_JUMP`（默认 8）太大或太小：把 ch5/ch6 记下来和真实拐点比
   - 乱跳（直道上也报）→ 把 `RING_JUMP` 调大、或 `RING_WHITE_MIN`/`RING_TRANS_MIN` 调严
2. **再调状态推进**：`RING_IN_LOST_MIN`（进环）和 `RING_OUT_LOST_MAX`（出环）要按实车的丢线数改，
   参考 ch0/ch1 的数值
3. **圆环目前只做识别，没有补线**。真正跑圆环还需要：
   - 识别到圆环后**不再跟随圆环外沿**（否则车会顺着环转出去）
   - 用陀螺仪积分辅助出环（文章里也提到"此时对陀螺仪进行积分，辅助出环"）
   这两块要等识别稳定之后再补。
