# 图像处理代码总览（当前版本）

> 这份文档讲清楚"一帧图像从摄像头进来，到最后画面上那三条线是怎么算出来的"。
> 按**数据流顺序**讲，每步都说明：**输入是什么、输出去哪、为什么要这么做**。

---

## 〇、一句话总览

```
灰度图 → 二值化 → 从车头那行往上"爬"着找边线 → 遇到十字/圆环特殊处理 → 后处理修毛刺 → 贴边 → 显示
```

**所有结果的载体只有三个数组**（下标=行号，值=列坐标）：

| 数组 | 含义 | 谁写它 |
| --- | --- | --- |
| `track_left[120]` | 每行左边线的列坐标 | 寻线 / 十字补线 / 圆环补线 / 后处理 / 贴边 |
| `track_right[120]` | 每行右边线的列坐标 | 同上 |
| `track_center[120]` | 每行中线的列坐标 | 上面每步做完都会重算 |

**辅助数组**：

| 数组 | 含义 |
| --- | --- |
| `track_lost[120]` | 每行的丢线标志：bit0=左线丢、bit1=右线丢。**这个数组非常关键**，十字/圆环的识别和补线全靠它 |
| `track_left_lost_count` / `track_right_lost_count` | 左右各丢了多少行（示波器 ch0/ch1） |
| `track_interp_count` | 后处理插值补了多少行（示波器 ch7） |

---

## 一、主循环：一帧走 6 步

`user/main.c` 里，`mt9v03x_finish_flag` 置位后依次执行：

```
① image_threshold_calc(mode)   求二值化阈值
② image_binarize(image_copy[0]) 二值化  —— 同时也完成了"图像备份"
③ track_edge_process()          寻线（种子生长）
④ cross_road_process()          十字识别 + 补线   ← 会改 track_left/right
⑤ ring_road_process()           圆环识别 + 补线   ← 会改 track_left/right
⑥ track_line_smooth()           丢线插值 + 中值滤波 + 重算中线
⑦ track_pin_lost_edges()        跑出画面的边线贴到画面边上
   assistant_oscilloscope_send() 发 8 通道诊断数据
   seekfree_assistant_camera_send() 发图像 + 三条边界线
```

**顺序为什么不能乱**：

- ④⑤ 必须 **在 ⑥ 之前**：十字/圆环补线要靠 `track_lost` 的**原始**丢线标志判断该补哪些行，
  而 ⑥ 会把丢线行插值掉（数组值变了，但 `track_lost` 标志不清，所以其实靠的是标志没被清）
- ⑦ 必须在 **⑥ 之后**：它要覆盖 ⑥ 插值出来的"飘在画面中间"的值
- ① 和 ② 里，`image_binarize` **同时**把当前帧写进 `image_copy`，
  这样就不需要再申请一块 120×188 的图像数组（省 22.5KB RAM）

## 二、① 二值化：把灰度图变成黑白

```c
image_threshold_calc(IMAGE_THRESHOLD_MODE);   // 求阈值
image_binarize(image_copy[0]);                // 逐像素比较
```

**当前配置**：`IMAGE_THRESHOLD_MODE = IMAGE_THRESHOLD_MODE_MANUAL` → **固定阈值 150**。

```c
// 逐像素：
if (mt9v03x_image[i][j] > 150)   image_copy[i][j] = 255;   // 白 = 赛道
else                             image_copy[i][j] = 0;     // 黑 = 背景
```

**三个模式可选**（改 `IMAGE_THRESHOLD_MODE`）：

| 模式 | 做法 | 特点 |
| --- | --- | --- |
| `MANUAL` | 固定 150 | 最快、最稳，但换光线要重标 |
| `OTSU` | 大津法（类间方差最大） | 自适应光线，但阈值随画面内容浮动 |
| `ITERATION` | 迭代法（两组均值取中值迭代） | 介于两者之间 |

另外 `IMAGE_MANUAL_COMPARE_AUTO = 1` 时，**手动模式下也会顺便算一次大津法**，
结果放进 `image_threshold_auto`（示波器 ch2），只是为了让你**观察光线有没有整体变化**，
**不参与二值化**。

> ⚠️ 不要拿 ch2 当标定值用 —— 它随画面里赛道/背景占比变化，同一场地会在 159~182 之间浮动。

## 三、② 寻线：种子生长法（这是最核心的一步）

代码在 `code/track_edge.c`。

### 3.1 整体思路

**从最下面一行（车头，第 119 行）开始，一行一行往上找边线；每一行以上一行的边线位置为"种子"，
在种子附近搜索这一行的真实边线。**

```
第119行（车头）：用"三像素判据"从中线往两边扫，找到起点
第118行：以第119行的边线为种子，在 ±5 像素内找
第117行：以第118行的边线为种子，……
   ……
第  0行（最远）
```

**为什么用这种"爬"的方式而不是每行都全图扫**：
- 快：每行只看种子附近的几个像素（±5），不是 188 个
- 抗噪：赛道外的白色噪点不会把边线带跑（因为它离种子远）

### 3.2 起点怎么找：`track_first_scan`

在第 119 行（车头正下方，赛道一定在视野里），从图像中线 `MT9V03X_W/2` 开始：

- **往左扫**：找到第一个 `黑-黑-白` 的三像素组合 → 左边线
- **往右扫**：找到第一个 `白-黑-黑` 的三像素组合 → 右边线

**为什么是三个像素而不是一个跳变**：单个跳变很容易被噪点骗到；
要求"连续两个黑 + 一个白"（或反过来）能滤掉大部分孤立噪点。

### 3.3 每一行怎么找：`track_follow_scan`

对左边界（右边界同理，方向相反）：

```c
for (k = 0; k <= TRACK_SEED_BOX; k++)     // TRACK_SEED_BOX = 5
{
    if (k == 0)  试 seed_left         本身
    else
    {
        先试 seed_left - k    （外侧，远离赛道中心）
        再试 seed_left + k    （内侧）
    }
    命中就 break
}
```

**半径由小到大逐圈扩大**，含义是"**优先相信边线没有移动**"：
- k=0 命中（边线没动）→ 最快
- k=1、2… 逐圈往外找，**先试外侧再试内侧**

**每行只搜 11 个位置**（±5），所以整帧寻线非常快。

### 3.4 三像素判据：`track_hit_left` / `track_hit_right`

```c
// 左边界：往右看应该是 黑-黑-白
static uint8 track_hit_left(image, row, c)
{
    return (c-1 是黑) && (c 是黑) && (c+1 是白);
}

// 右边界：往右看应该是 白-黑-黑
static uint8 track_hit_right(image, row, c)
{
    return (c-1 是白) && (c 是黑) && (c+1 是黑);
}
```

> 为什么左边界是"黑黑白"？因为左边线左边是背景（黑）、右边是赛道（白），
> 从左往右看过去就是"黑 → 黑 → 白"这个过渡。

### 3.5 找不到了怎么办：两层兜底

**第一层：本行保持上一行的值**（保证画出来的线不断）

```c
if (没找到 || left >= right)      // 左右交叉说明两边都跟丢了
{
    left  = seed_left;            // 保持上一行的值
    right = seed_right;
}
```

**第二层：连续丢 5 行 → 全局重捕获**（`TRACK_RECOVER_LOST = 5`）

```c
if (!found_left)
{
    track_lost_run[0]++;
    if (track_lost_run[0] >= 5)
    {
        // track_global_left: 从中线往左全图扫，找第一个"黑黑白"
        if (track_global_left(image, row, &rec)) { left = rec; found_left = 1; }
    }
}
```

**这一层非常重要**：种子一旦跟丢（比如经过十字的横杠），
如果不做全局重捕获，**上面整片都会一直丢线**，再也回不来。

> 这就是文章里的"第一种寻线"（从中线往两边扫寻找黑白跳变点），
> 被我们当成"第二种寻线的救援机制"来用。

### 3.6 记录结果

每一行处理完，写四个地方：

```c
track_left[row]   = left;
track_right[row]  = right;
track_center[row] = (left + right) / 2;
if (!found_left)  { track_lost[row] |= 0x01; track_left_lost_count++;  }
if (!found_right) { track_lost[row] |= 0x02; track_right_lost_count++; }
```

**`track_lost` 是给十字/圆环模块用的**：它们不重新扫图像，直接看"哪些行丢了"。

## 四、③ 十字识别与补线（`code/cross_road.c`）

### 4.1 十字长什么样

```
        ┌───────────────┐   ← 远端赛道
   ─────┘               └─────
   ═══════════════════════════  ← 横杠（把左右边线全盖住了）
   ─────┐               ┌─────
        └───────────────┘   ← 近端赛道
```

**关键特征**：横杠那一段，**左右边线同时丢线**（因为它们都被横杠盖住了）。

### 4.2 怎么识别：两阶段

**第一阶段：预扫线**（`cross_prescan` + `cross_scan_column`）

对**每一列**，从上往下找出"白区"，并挑出**离图像中间行最近的那一段**，
记录它的上边界 `cross_up_y[x]` 和下边界 `cross_down_y[x]`。

得到两条**一维轮廓曲线**：

```
cross_up_y[]   : 每一列"白区最上面"在哪一行
cross_down_y[] : 每一列"白区最下面"在哪一行
```

十字的横杠在 `cross_up_y` 上表现为一段**平坦的台子**，在赛道边界处**突然跳变**。

**第二阶段：找 4 个 L 角点**（`cross_find_corner`）

沿着 `cross_up_y` 从左往右扫，找"纵坐标开始变小"的点 → **左上角点**；
从右往左扫 → **右上角点**；`cross_down_y` 同理 → 左下、右下角点。

### 4.3 预识别条件（`cross_pre_check`）

必须**同时**满足才会进入十字状态：

| 条件 | 内容 | 参数 |
| --- | --- | --- |
| 1 | 左右丢线总数够多，且至少一侧够多 | `CROSS_LOST_SUM_MIN=30`、`CROSS_LOST_MIN=15` |
| 1.5 | **左右"同时丢线"的行数够多**（十字的铁证） | `CROSS_OVERLAP_MIN=3` |
| 3 | 中间区域存在一行几乎全白（横杠） | `CROSS_CENTER_WHITE_MIN=150` |
| 4 | 图像中间矩形内白点够多 | `CROSS_RECT_WHITE_MIN=2000` |
| 角点 | 远端两个角点都在，近端至少一个 | — |

> **条件 1.5 是区分圆环的关键**：圆环入口只有一侧道路张开（另一侧是直道），
> 十字的横杠会把左右**同时**盖住。
>
> 原来还有一条"参考横线上有丢线"（照文章写的，写死在第 55/80 行），
> **已经删掉** —— 横杠在图像上部时那两行根本没被盖住，会导致十字完全识别不出来。

### 4.4 状态机（3 个状态）

| 状态 | 含义 | 推进条件 |
| --- | --- | --- |
| `NONE(0)` | 不在十字 | 预识别条件 + 远端两角点 → `IN` |
| `IN(1)` | 刚进入十字 | 上方角点消失（已经开进横杠了）→ `INSIDE` |
| `INSIDE(2)` | 十字里面 | 下方角点出现 → `OUT` |
| `OUT(3)` | 出十字 | 丢线数降下来 → `NONE` |

### 4.5 补线（`cross_fix_side`）—— 两条路

对**每一条边线单独判断**，看它的**上角点**和**下角点**在不在：

**方式 A：上下角点都在** → 直接**两点连直线**

```
上角点 ─┐
        │  ← 这条连线就是补出来的边线
下角点 ─┘
```

**方式 B：只有上角点** → 用角点**上方 10 行**的有效值做**最小二乘拟合**，
把这条直线**往下延长到"横杠下沿"**（`cross_bar_bottom`）。

> 如果拟合点数不够（角点上方有效行太少），**退化成"角点 + 上方最近一个有效点"两点连线**，
> 不能直接放弃 —— 放弃的话那一段就不补了，画出来是一截竖线。

**横杠下沿怎么估**（`cross_estimate_bar`）：
在两个上角点**之间**的区域之外，取 `cross_down_y` 的**中位数**。

## 五、④ 圆环识别与补线（`code/ring_road.c`）

### 5.1 圆环长什么样

```
   ┌─────────────┐
   │   环岛      │ ← 环内侧（黑色的岛）
   │  ┌───────┐  │
   └──┘       └──┘ ← 环外侧
```

**关键特征**：圆环是**接在直道旁边**的，所以：

- **入口那一侧**：道路向这一侧张开 → 那一条边线**连续丢一大段**
- **对面那一侧**：还是直道 → 边线**又直又完整**

### 5.2 怎么识别（`ring_try_side`）—— 4 个条件

| 条件 | 内容 | 参数 |
| --- | --- | --- |
| 1 | **对面是连续直道**：丢线少 + 拟合后偏差的**中位数**小 | `RING_STRAIGHT_LOST_MAX=10`、`RING_STRAIGHT_DEV_MAX=6` |
| 2 | **入口侧有一段足够长的连续丢线**（道路张开） | `RING_OPEN_LOST_MIN=25` |
| 2' | 找不到长丢线段时，退回用文章方法一的"**向外张开的拐点**" | `RING_JUMP=8` |
| 3 | **对面自己也不允许有太长的连续丢线段** | `RING_OPPO_RUN_MAX=15` |
| 4 | **张开那一段行范围里，对面基本不丢线** | `RING_OPPO_LOST_MAX=8` |

> **条件 4 是区分圆环和十字的关键**：十字两边同时丢线，圆环只丢一边。
>
> **直线度为什么用中位数不用最大值**：边界数组里偶尔有几行是离群点（种子行误差、跳变），
> 用最大值会被这几行拉爆（实测到 58 像素），用中位数就只剩几个像素。

### 5.3 状态机（4 个状态）

| 状态 | 含义 | 推进条件 |
| --- | --- | --- |
| `NONE(0)` | 不在圆环 | 上面 4 个条件 → `FIND`（同时记下是左环还是右环） |
| `FIND(1)` | 识别到入口 | 入口侧丢线 ≥ `RING_IN_LOST_MIN(35)` → `IN` |
| `IN(2)` | 正在进环 | 找到环内特征（全白行/跳变行）→ `INSIDE` |
| `INSIDE(3)` | 在环里 | 入口侧丢线 ≤ `RING_OUT_LOST_MAX(12)` → `OUT` |
| `OUT(4)` | 出环 | 丢线继续减少 → `NONE` |

另外有**超时保护**：连续 `RING_STATE_TIMEOUT(200)` 帧没推进就强制复位，防止卡死。

### 5.4 补线（`ring_fix_side`）—— 相对"对面那条可靠边线"来补

| 状态 | 怎么补 |
| --- | --- |
| 入环（1/2） | 圆环侧边线 = **对面边线 ± 赛道宽度 ± 入环偏移**（偏移从 0 线性加到上限 30） |
| **环内（3）** | **不补** —— 环内的白区就是环的路面，正常寻线得到的中线就能走 |
| 出环（4） | 圆环侧边线 = **对面边线 ± 赛道宽度**（偏移 0）→ 与对面平行 → 车直着出去 |

**赛道宽度**是用"入口拐点以**下**那一段"（正常的直道）统计出来的 ——
那一段两条边线都可靠。

> **为什么必须相对对面来补**：第一版是"从拐点往上按固定斜率推"，没有上限，
> 结果边界被一路推到图像边缘（第 187 列），中线跟着偏向环外侧，车就冲出环外了。

## 六、⑤ 后处理（`track_line_smooth`）

补线做完之后，对两条边线各做两件事：

**1. 丢线行插值**（`track_fill_lost_side`）

对每一段连续丢线 `[a, b]`，用它**下面那个有效值** `edge[a-1]` 和**上面那个有效值** `edge[b+1]`
连一条直线填进去。

**2. 中值滤波**（`track_median_side`）

单行毛刺去掉（`TRACK_MEDIAN_ENABLE`）：如果某一行的值和上下两行的中位数差太多，就用中位数替换。

**3. 重算中线**（`track_center_update`）

```c
track_center[row] = (track_left[row] + track_right[row]) / 2;
```

## 七、⑥ 丢线贴边（`track_pin_lost_edges`）

**连续丢线 ≥ 12 行，而且丢线前那一段已经贴近画面边缘（≤30 像素）**
→ 说明这条边线**跑出画面**了，把整段**直接贴到画面边上**（左线贴第 0 列，右线贴第 187 列）。

**为什么要加"贴近边缘"这个前提**：十字和圆环也有长丢线段，
但它们的端点在画面中间（横杠边缘、环岛边缘），**不能贴边**。
实测：十字 **0 行**被贴边，大弯道 curv=60 有 **94%** 的丢线行被贴边。

## 八、为什么你觉得代码"怪"

**说实话：因为它是层层打补丁叠出来的。** 发展过程是这样的：

| 阶段 | 加了什么 | 为什么加 |
| --- | --- | --- |
| 1 | 二值化（迭代法/大津法） | 最初的需求 |
| 2 | 固定阈值 | 你要稳定 |
| 3 | 种子生长寻线 | 文章第二种寻线 |
| 4 | **全局重捕获** | 种子跟丢后回不来 |
| 5 | **中值滤波** | 边线有单行毛刺 |
| 6 | 十字识别 + 补线 | 文章第三种 |
| 7 | 十字"同时丢线"条件 | 圆环入口被误判成十字 |
| 8 | 十字"退化补线" | 拟合点数不够时那一段没补 |
| 9 | 圆环识别（4 条件） | 文章第四种 |
| 10 | 圆环补线（改了两版） | 第一版把边界推到图像边缘 |
| 11 | **丢线贴边** | 大弯道边线出画面后"乱飘" |

结果就是：**一个主流程 + 两个状态机 + 三个补线函数 + 一个后处理**，
而且它们**互相覆盖**（后面的覆盖前面的结果），所以初看会觉得很乱。

**具体"怪"的地方**：

1. **`track_left/right` 被反复改写** —— 寻线写一次、十字改一次、圆环改一次、后处理再改一次、贴边最后改一次。
   好处是每步只管自己的事；坏处是**调试时很难知道某个值是谁写的**。
2. **`track_lost` 标志和 `track_left/right` 的值会"不同步"** ——
   补线改了值但没清标志，后处理又按标志去插值。这是**故意的**（十字/圆环需要原始标志），
   但很容易看糊涂。
3. **通道 ch5/ch6 是共用的** —— 十字激活时报十字角点，否则报圆环的，看的时候要先看 ch3/ch4。
