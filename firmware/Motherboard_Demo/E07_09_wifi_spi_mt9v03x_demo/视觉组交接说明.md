## 二、开工前必须知道的约定

### 2.1 编码：所有源文件是 **GBK + CRLF**

**这是最容易踩的坑。** 编辑流程必须是：

```powershell
# 改之前：GBK -> UTF-8
$gbk = [System.Text.Encoding]::GetEncoding(936)
[System.IO.File]::WriteAllText($p, [System.IO.File]::ReadAllText($p, $gbk), (New-Object System.Text.UTF8Encoding($false)))
# ... 用编辑工具改 ...
# 改完：UTF-8 -> GBK
[System.IO.File]::WriteAllText($p, [System.IO.File]::ReadAllText($p, [System.Text.Encoding]::UTF8), $gbk)
```

**直接用编辑工具改 GBK 文件会读不出来**（报 "invalid UTF-8 text"）。

### 2.2 编译

请使用仓库根目录的 `build.ps1`，编译环境和操作步骤以根目录 README 与 `docs/getting-started.md` 为准。

### 2.3 PowerShell 里的中文坑

**双引号字符串里出现中文全角引号 `"` `"` 会让 PowerShell 解析失败。**
写脚本时用**单引号 here-string**（`@'...'@`），不要用双引号包中文注释。

### 2.5 帧率问题的完整结论（**已经解决，别再走弯路**）

用户提过"帧率太低，能不能改隔行搜索"。**结论：隔行【搜索】没用，隔行【发送】才有用。**

**为什么帧率低**（算给任何人看）：

```
SPI 速率          48 MHz          ← 已经很快，不是瓶颈
每次传输上限      4088 字节       ← WiFi 模块限制，不能改
每帧图像          22560 字节      （188 × 120）
实测无线带宽      115~140 KB/s
────────────────────────────────────────────
22560 ÷ 120000 ≈ 188 ms/帧  →  5.3 fps
（和逐飞助手显示的 5~7 fps、字节数/秒 115~140K 完全吻合）
```

> **帧率 = 无线带宽 ÷ 每帧字节数。算法再快也没用。**

**隔行搜索为什么不行**（仿真实测，格式：边线误差像素 / 丢线行数）：

| 场景 | 逐行（现在） | 隔行(step2) | 隔3行 |
| --- | --- | --- | --- |
| 干净直道 | 1.98 / 0 | 3.43 / 2 | 30.83 ✗ |
| 抖1px | 2.19 / 0 | 3.71 / 2 | 30.92 ✗ |
| 散粒1% | 3.34 / 4 | 6.70 / 12 | 31.55 ✗ |
| 弯道40 | 2.31 / 14 | 3.71 / 17 | 31.58 ✗ |
| 弯道40+抖+散粒 | 14.60 / 20 | 17.70 / 32 | 42.99 ✗ |

误差涨 40%~100%，而且省下的计算量（探测次数 540→305）**只占每帧总时间的不到 1%**。

**已经改成"隔行发送"**（`user/main.c`）：

| 宏 | 当前值 | 含义 |
| --- | --- | --- |
| `CAMERA_SEND_STEP` | 2 | 隔几行发一行 |
| `CAMERA_SEND_H` | 60 | 发送图像高度 |
| `CAMERA_SEND_INTERVAL` | 1 | 每几帧发一次图 |

- 每帧字节数 **22560 → 11280**，帧率预期 **5~7 → 10~14 fps**
- **算法完全不受影响**：寻线/十字/圆环还是在完整 120 行上跑
- 抽取的行是 **1、3、5 … 119**（包含第 119 行 —— 车头那行、寻线起种那行，调试最关键）
- 三条边线 `send_left/send_center/send_right[60]` 同步隔行抽取，长度和图像高度一致

**⚠️ 遗留隐患（加电机控制之前必须解决）**

`seekfree_assistant_camera_send()` 是**阻塞**的 —— 11280 字节在 115~140 KB/s 上要 **80~100 ms**，
这段时间**整个主循环都停在这里**。现在没有电机控制只影响调试；
**一旦加上 PID + 电机，控制频率也会被拖到 10 fps 左右，车根本跑不了。**

解法（按优先级）：
1. 把 `CAMERA_SEND_INTERVAL` 调大（图像少发几帧）→ 处理频率立刻上去
2. 把发送挪到中断/DMA 后台
3. 用另一个物理通道发调试数据（主板上有无线转串口模块，UART8，P9.2/P9.3/P9.4，**和 WiFi SPI 无引脚冲突**）

**示波器数据（8 通道 × 4 字节 = 32 字节）每帧都在发，不受发图影响** —— 调参看它是实时的。

## 三、代码结构（一帧的完整流程）

主循环在 `user/main.c`，`mt9v03x_finish_flag` 置位后依次执行：

```
① image_threshold_calc(mode)       求二值化阈值
② image_binarize(image_copy[0])    二值化（同时完成"图像备份"，省 22.5KB RAM）
③ track_edge_process()             寻线（种子生长法）
④ cross_road_process()             十字识别 + 补线   ← 改 track_left/right
⑤ ring_road_process()              圆环识别 + 补线   ← 改 track_left/right
⑥ track_line_smooth()              丢线插值 + 中值滤波 + 重算中线
⑦ track_pin_lost_edges()           跑出画面的边线贴到画面边上
   assistant_oscilloscope_send()   发 8 通道诊断数据
   seekfree_assistant_camera_send() 发图像 + 三条边界线
```

**顺序不能乱**：④⑤ 必须在 ⑥ 前（补线要靠原始丢线标志）；⑦ 必须在 ⑥ 后（要覆盖插值结果）。

### 核心数据（所有模块的公共接口）

```c
uint8 track_left[120];     // 每行左边线的列坐标
uint8 track_right[120];    // 每行右边线的列坐标
uint8 track_center[120];   // 每行中线的列坐标
uint8 track_lost[120];     // 丢线标志 bit0=左线丢 bit1=右线丢  ← 十字/圆环全靠它
uint16 track_left_lost_count, track_right_lost_count;
uint8 track_interp_count;  // 被插值补上的行数
```

**坐标约定**：行号 **0 = 最远（图像上方）、119 = 车头（下方）**。
摄像头**反装**的话要改 `TRACK_START_ROW=0` / `TRACK_ROW_STEP=+1`，并左右对调。

### 各模块文件

| 文件 | 职责 | 详细文档 |
| --- | --- | --- |
| `code/image_process.c/h` | 二值化（固定阈值 / 大津法 / 迭代法） | `二值化说明.md` |
| `code/track_edge.c/h` | 种子生长法寻线 | `寻线详解.md`、`寻线说明.md` |

## 五、**待办与未验证项**（接手后优先看这里）

### 5.1 用户当前最关心的问题

**某个特定位置的十字补线补不出来**（边线在那里变成一截竖线）。

已经加了诊断通道，**在等用户的数值**：

| 通道 | 含义 |
| --- | --- |
| `ch3` | 十字状态（0=不在 / 1=进入 / 2=十字内 / 3=出十字） |
| **`ch5`** | **左上角点所在行**（0 = 没找到） |
| **`ch6`** | **左下角点所在行**（0 = 没找到） |

> **补线的行范围就是 `[ch5, ch6]`。** 让用户在那个位置停住，发 `ch0 / ch1 / ch3 / ch5 / ch6` 五个数。

**定位表**：

| 现象 | 原因 | 怎么改 |
| --- | --- | --- |
| `ch3 = 0` | 十字根本没识别 | 改预识别条件（`cross_pre_check`） |
| `ch5 = 0` | 左上角点没找到 | 角点检测（`CROSS_CORNER_TOL` 或曲线形状） |
| `ch6 = 0` | 左下角点没找到 | 只能走方式 B，依赖横杠下沿估计 |
| 都有但范围太窄 | 横杠下沿估错 / 角点行号不对 | `cross_estimate_bar` |
| 都正常但线不对 | 拟合斜率或锚点 | `cross_fix_side` |

## 六、调试体系（**这是这个项目最有价值的部分**）

### 6.1 虚拟示波器 8 通道

| 通道 | 内容 |
| --- | --- |
| `ch0` | 左线丢线行数 |
| `ch1` | 右线丢线行数 |
| `ch2` | **大津法自动阈值**（只用来观察光线变化，**不参与二值化**） |
| `ch3` | 十字状态 |
| `ch4` | 圆环：识别到 = 类型×10+状态（11~14 左环，21~24 右环）；<br>没识别到 = **负数失败原因**：`-2` 入口没张开、`-3` 更像十字、<br>`-11` 对面丢线多、`-12` 点太少、`-13` 拟合退化、`-14` 不够直 |
| `ch5` | 十字激活时 = 左上角点行；否则 = 圆环入口拐点行 / 拟合偏差 |
| `ch6` | 十字激活时 = 左下角点行；否则 = 圆环入口拐点列 / 对面丢线数 |
| `ch7` | 被插值补上的行数 |

**ch5/ch6 是共用的，看之前先看 ch3/ch4。**

### 6.2 ⚠️ 一条血泪教训

**不要拿 `ch2`（大津法）去标定固定阈值。**

`ch2` 会随画面里赛道/背景的占比变化，同一场地实测在 **159~182** 之间浮动。
曾经有一版按某一帧的 ch2=182 把手动阈值从 150 改成 180，**那是错的**，已改回 150。

**判断阈值合不合适只看图像**：背景大片变白 = 阈值偏低；赛道被吃掉变黑 = 阈值偏高。

### 6.3 仿真回放模板

每个模块都有一套 Python 仿真（临时文件，没留在工作区）。**要复用的话照这个结构重建**：

```
1. 合成场景（直道/弯道/十字/圆环/带噪声，随机种子跑多组）
2. 把 C 算法移植成 Python（逐函数对应，保持逻辑一致）
3. 跑算法，和"真值"逐行比较
4. 输出：平均误差(像素) / 丢线行数 / 检测率 / 误报率
5. 对比"改前 vs 改后"
```

**判据**：改了之后数字要**变好**才落地；没有数据支撑的改动不做。

## 九、这个项目的技术要点速查

| 要点 | 内容 |
| --- | --- |
| **寻线为什么用种子生长** | 每行只搜 11 个位置（±5），比全图扫快 17 倍，而且赛道外的白噪点进不了搜索窗口 |
| **三像素判据** | 左边界 `黑-黑-白`、右边界 `白-白-黑`。单跳变会被孤立噪点骗到 |
| **全局重捕获** | 连续丢 5 行 → 从中线全图重扫。**没有它，种子在十字横杠跟丢后上面整片再也回不来** |
| **十字的本质** | 横杠把左右边线**同时**盖住 |
| **圆环的本质** | **只有一侧**道路张开（另一侧是直道）→ 这是区分圆环和十字的唯一依据 |
| **`CROSS_OVERLAP_MIN`** | "左右同时丢线的行数"。实测：正入十字 39 行、斜入 29 行、**圆环入口 0 行** |
| **直线度为什么用中位数** | 边界数组偶尔有几行离群，**最大值会被拉爆到 58 像素**，中位数只剩 2 像素 |
| **补线为什么要"无条件覆盖"** | 横杠区域里寻线会找到**横杠自己的边**，那些行**没被标成丢线**，只补丢线行会漏掉一整段 |
| **两段拟合为什么要角点校验** | 斜入时拟合点会混进横杠的边，整条线被带偏（大误差行数 8→33） |
