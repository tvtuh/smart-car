# 智能车闭环控制说明（E07_09 工程）

> 目标：让车沿着左右两条边线之间的**中线**跑。
> **视觉接口以视觉组给的 `main.c` 为准**：`x2_boundary[row] = 左边界`、`x3_boundary[row] = 右边界`（行 0 = 最远），
> 中线由本工程自己按 `(左 + 右) / 2` 算；视觉算法**一个字没动**，只在它上面加了整车控制挂钩。

## 2. 控制结构（数据怎么流的）

```
mt9v03x 摄像头
   └─ 视觉算法（视觉组给的，未改）：x2 = 左边界、x3 = 右边界（每行都有值；找不到线时用种子值兜底）
          x1 本来他们不发（恒 0），本工程在 main.c 的挂钩里把中线写进 x1，
          这样逐飞助手画面上的三条线依次是 左 / 中 / 右，看图调参直观；视觉算法不使用 x1
        └─ car_control_update()  ← 每帧调用一次
             ├─ 近/中/远三行中线（100/80/58 行）加权 → 瞄点误差 aim
             │      └─ PD → 打角量 steer（度）→ 舵机（前轮）
             ├─ 弯道程度 = |远行偏移 − 近行偏移| → 目标速度 speed
             │      └─ 差速：内轮 speed−diff、外轮 speed+diff
             └─ motor_set_target(左, 右)  ← 单位 cm/s
                  └─ 10ms 定时中断里的速度环（固定 100Hz）
                       ├─ 读编码器 → 实测速度
                       ├─ 前馈 + PI → 占空比
                       ├─ 输出斜坡（每次最多 ±200/10000）
                       └─ 写 DIR + PWM → DRV8701E → 后轮双电机
```

要点：

- **打角每帧更新一次**（跟图像帧率走），**速度环固定 100Hz**（跟 10ms 中断走），两者解耦。
- `image_update_yellow_boundary() → car_control_update() → 上传图像`，先算控制量再传图，控制延迟最小。
- **十字 / 丢线**：视觉组那份里**没有** `track_type` 这类标志（它总是用种子值把线补出来），所以本工程自己判：
  三行宽度都不可信时——短暂 → 按十字处理（中线取画面中心 => 直行，同时压速到 `CAR_SPEED_CROSS_CM_S`）；
  持续 `CAR_OPEN_AS_LOST_FRAMES` 帧以上 → 按丢线处理（保持打角 + 爬行，久丢停车）。
- **丢线**：保留 70% 上一帧打角（不回正，否则弯道丢线直接冲出去）+ 爬行速度；连续丢线超过 80 帧直接停车。

> **关于舵机口**：已确认为 **PA6（PWM4，从上往下第 4 个）**，配置里就是它。
>
> 顺便留个记录，免得以后换线时又插错位置：**P22 不能用**。
>
> - `zf_device_mt9v03x.h` 里 `MT9V03X_D2_PIN = IO_P22` —— P22 是摄像头的数据位 D2，这个摄像头走 FIFO+DMA，每帧都在驱动 P22。
> - 舵机例程 E02_03 里主板 4 个舵机口是 `PA0 / PA2 / PA4 / PA6`，**整个 SDK 例程没有一处用到 P22**。
> - 真往 P22 输出 50Hz PWM 的后果：舵机被图像数据抽得乱抖（可能堵转发热），图像也会因为 D2 被拉坏出现条纹。
>
> 日后万一日换了线或换了板子，用 **E02_03 舵机例程**当场验证：它一次驱动 4 个口，舵机插在哪个口就在哪个口来回摆，10 秒就能确认。

### 第 1 步：台架自检（**车轮悬空！**）

`car_config.h` 里设：

```c
#define CAR_BRINGUP_TEST  (1)
```

**先搞清楚"数字在哪看"**——编码器本身没有显示屏，它只是"轮子转一圈发 N 个脉冲"的传感器，
数值只能由单片机读出来、再由单片机的串口告诉你：

- 这个工程的 `printf` 走的是 **USB 虚拟串口**（`zf_common_debug.h` 里 `USER_USB_CDC = 1`，
  `debug_init()` 调的是 `usb_cdc_init()`），所以**一根 USB 线把核心板接到电脑就够**，不用另接串口模块、不用 USB 转 TTL。
- 电脑上开串口助手（**STC-ISP 自带的"串口助手"标签页就能用**，或任意串口助手/逐飞助手），
  选**核心板那个 USB 串口**：烧录完成后 MCU 会以"USB 串行设备"再枚举出一个新 COM 口，
  它未必和烧录时的口是同一个号，拔插一下看多出来的是哪个；波特率填 **115200**（USB 虚拟串口其实不看波特率，填什么都行）。
- 上电后先出现 `===== BOOT OK =====` / `step1 OK: clock + debug uart`，接着就是自检的打印。

**自检不需要热点、不需要逐飞助手、不需要摄像头**：`car_config.h` 里 `CAR_BRINGUP_SKIP_VISION = 1`
（默认就是 1）。main.c 本来按"先连 WiFi → 再连逐飞助手 → 再初始化摄像头"的顺序走，
**任一步失败都会一直在那里重试**，而台架自检只用到舵机/电机/编码器，所以自检模式下这三步直接跳过，
只插 USB 就能看到输出。正式跑车时 `CAR_BRINGUP_TEST = 0`，这个开关自动失效，视觉链路照常。

> ### ★ fw16：为什么以前 `CAR_BRINGUP_TEST = 0` 时"串口助手完全没数据"
>
> 视觉链路三步的重试，**库里每一步的超时都非常大**：
>
> | 库里的宏 | 一次要等多久 |
> |---|---|
> | `WIFI_CONNECT_TIME_OUT`（连热点） | **10 秒** |
> | `SOCKET_CONNECT_TIME_OUT`（连 TCP） | **50 秒** |
>
> 而无线串口的初始化（在 `car_control_init()` 里）原来排在**这三步后面**，所以：
> `CAR_BRINGUP_TEST = 1`（跳过视觉链路）→ 1 秒就有数据；
> `CAR_BRINGUP_TEST = 0`（要视觉，上赛道的正确配置）→ 先干等"连热点 + 连 TCP + 摄像头"的重试，
> **串口助手一直空白**，看起来像模块坏了或者程序没跑。
>
> fw16 三件事一起修：
> 1. **开机第 1 秒就把无线串口点亮**（`car_wireless_link_init()` 提到 `debug_init()` 之后），
>    后面每一步都往串口助手里报进度：`boot: joining wifi hot-spot ...` / `boot: init camera ...`；
> 2. `CAR_VISION_TRY_MAX` 从 60 改成 **2**（连热点最多 20 秒）；TCP 那一步单独由
>    `CAR_WIFI_TCP_CONNECT` 控制，**默认 0 = 不连**（不连就不会卡 50 秒，跑车和数字上报都不受影响）；
> 3. 开机阶段在串口助手里发 **`x`** 可以**立刻跳过整条视觉链路**，不用等。
>
> 结论：**上赛道就该用 `CAR_BRINGUP_TEST = 0`（要视觉）**，不需要为了"串口有数据"把它设成 1。

> 想在车上直接看数字也可以（不插电脑）：加一块 IPS200 / TFT180，照 `E06_xx` 例程把数值显示出来。
> 但调参阶段串口最方便，建议先用串口。

上电后串口会依次打印并执行：舵机 左(-20°)→中→右(+20°)→中，然后**左轮转 1.5s、右轮转 1.5s**，最后分两步（先只转左轮、再只转右轮）让你用手转车轮并打印编码器计数。逐项确认：

> **转轮子那两段是"纯开环"的**（`car_config.h` 里 `CAR_TEST_DUTY`，默认 20% 占空比，不看编码器、不跑速度环）。
> 为什么这么设计：自检时编码器接线还没验证，如果这时候用闭环，编码器读数一乱，速度环就会把电机
> **一会儿正转一会儿反转**（看起来"轮子时前时后"），那就分不清是接线问题还是闭环在跟乱读数打架。
> 所以看方向必须纯开环；编码器好不好，靠后面那两步"用手转车轮"单独验。
> 轮子不转就把 `CAR_TEST_DUTY` 加大（2000 → 3000）。

| 检查项 | 期望 | 不对就改 |
|---|---|---|
| 打角 -20° | 前轮朝**左** | `CAR_SERVO_INVERT` 改成 1（或改回 0） |
| 打印 `LEFT wheel forward` 时 | 动的必须是**左轮**（不是右轮） | `CAR_SWAP_MOTOR_LR` 置 1 / 置 0 —— 这是"哪一侧"的问题 |
| 左轮"前进" | 轮子**往前**转 | `CAR_MOTOR_L_INVERT` 改成 1（或改回 0）—— 这是"正反转"的问题 |
| 右轮"前进" | 轮子**往前**转 | `CAR_MOTOR_R_INVERT` 改成 1（或改回 0） |
| 轮子**时前时后**、来回抖 | 不该出现（这两段是开环，只会朝一个方向转） | 说明是**外面**的问题：线松/DIR 接触不良，或 20% 占空比太小带不动+静摩擦来回蹭 → 加大 `CAR_TEST_DUTY` |
| 第 1 步（只转左轮 2 秒） | `encL` 为正、`encR` ≈ 0 | 动的是 `encR` → `CAR_SWAP_ENCODER_LR` 改一下；`encL` 是负数 → `CAR_ENC_L_INVERT` |
| 第 2 步（只转右轮 2 秒） | `encR` 为正、`encL` ≈ 0 | 动的是 `encL` → `CAR_SWAP_ENCODER_LR` 改一下；`encR` 是负数 → `CAR_ENC_R_INVERT` |
| 舵机左右极限 | 不堵转、不打齿 | 调 `CAR_SERVO_LEFT_DEG / RIGHT_DEG` |

> **"哪一侧"和"正反转"是两件不同的事，别混**：
> - `CAR_SWAP_MOTOR_LR` / `CAR_SWAP_ENCODER_LR` 管**哪一侧**（代码里的"左"到底是不是车的左）
> - `CAR_MOTOR_x_INVERT` / `CAR_ENC_x_INVERT` 管**正反转**（往前转还是往后转）
>
> 所以**改 `INVERT` 永远不会改变"哪个轮子先动"** —— 顺序是自检流程写死的（先左轮、后右轮）。
> 打印 `LEFT wheel` 却动了右轮，要改的是 `CAR_SWAP_MOTOR_LR`。

确认完全部改回 `CAR_BRINGUP_TEST 0`。

`car_config.h` 里上赛道的配置（fw15 已经这么配好了）：

```c
#define CAR_BRINGUP_TEST     (0)    // 上赛道必须 0：要跑视觉（自检模式会跳过整条视觉链路）
#define CAR_ENABLE_MOTOR     (1)    // 允许出力
#define CAR_ENABLE_ENCODER   (0)    // 第一圈先开环（固定占空比），少一个变量；跑顺了再改 1
#define CAR_BOOT_OUTPUT_OFF  (1)    // ★ 上电把输出硬关：车绝对不动，发 o 才出力
#define CAR_USE_WIFI_LINK    (1)    // 图像链路开着（IP / 逐飞助手由你自己配）
#define CAR_WIFI_TCP_CONNECT (1)    // 1 = 主动连上位机 TCP（**图像靠它才能传到逐飞助手**）；
                                    //   代价：IP/上位机没配好时，开机这一步最多卡 50 秒（库的超时）
#define CAR_SPEED_BASE_CM_S  (52)   // 52 x 40 = 20.8% 占空比（fw25 又放慢一档：先把直道跑稳）
```

**上电后按顺序做四件事**（整个过程车都不会自己动，很安全）：

1. **上电**（电池接好、车摆在赛道中线附近）。**1 秒内**串口助手里就会出现
   `[CAR] wireless uart ready, fw16 baud=115200`，接着是 `boot: joining wifi hot-spot ...` 之类的进度；
   之后约 5 秒起步延时 + 摄像头初始化，不用管；
   串口助手（无线模块，115200）会开始每 500ms 滚一行 `encL=.. spdL=.. dutyL=.. aim=.. steer=..`。
2. **发 `?`**，应回 `WV fw15: invL=0 invR=0 mode=0 socket=0 period=500ms output=0 bench=65cm/s steerinv=0`。
   注意 `output=0` —— 这就是"输出硬关"，车不会动。
3. **手推车，看前轮往哪打**（这一步最关键，打角方向反了车会直接冲出赛道）：
   - 把车**贴着中线**、车头朝前，慢慢往前推；
   - 车头偏到**中线左边** → 前轮应该往**右**打（往中线方向回）；
   - 车头偏到**中线右边** → 前轮应该往**左**打；
   - 同时看数字：`aim` 正 = 中线在画面右侧（车偏左），`steer` 的单位是 0.1 度、正 = 右打。
   - **如果方向反了**：无线串口发 **`n`**（打角整体取反，`?` 里 `steerinv=1`），再推一次确认；
     不用重新烧录，也不用改代码（想固定下来的话把 `CAR_STEER_INVERT` 改 1 重新烧一次）。
4. **确认方向对了 → 发 `o`**（输出解锁，`?` 里变成 `output=1`）→ 车开始跑。

> 为什么要"上电硬关 + 手推车"：一次烧录就能把"打角方向"这个最大的未知数在赛道上、车不动的情况下验掉。
> 打角方向错了车一给油就冲出赛道；这套流程把它变成"推着车走两步"就能发现的事。
> 想让电机重新停下：再发一次 `o`（硬关），或者直接断电。

**跑起来之后看这几个数**（无线串口，默认 500ms 一行，发 `+` 可以变快）：

| 数字 | 正常的样子 | 不对说明什么 |
|---|---|---|
| `aim` | 车在中线上时在 0 附近小幅抖动；车偏了就明显偏离 | 一直是 0 → 视觉没出数（摄像头没接好/线没找到）；乱跳 → 光照或阈值 |
| `steer` | 跟 `aim` 同号（`aim` 正 → `steer` 正） | 反号 → 发 `n` 取反 |
| `dutyL`/`dutyR` | 直道约 2080（20.8%），弯道降到 1800（18%） | 一直是 0 → 没发 `o` / 已 FAULT 锁死 / `CAR_ENABLE_MOTOR=0` |
| `encL`/`encR` | 前进时都是正数 | 负数 → `CAR_ENC_x_INVERT` |

**嫌快嫌慢都不用重新烧录**：无线串口发 **`u`**（每次 -5 cm/s）减速、发 **`i`** 加速，当前值看 `?` 里的 `vbase=`。
默认 `CAR_SPEED_BASE_CM_S = 52`（20.8% 占空比）；实在要改配置，一次动 10 以内，别一步到 90。

### 第 3 步：跑顺之后再考虑的事（可选，不影响"跑完一圈"）

| 想干的事 | 怎么改 | 值不值得 |
|---|---|---|
| 在逐飞助手里看图像（调试视觉最直观） | ① 电脑也连上 `REDACTED_WIFI_VALUE` 热点；② `ipconfig` 看 WLAN 的 IPv4；③ 把它填到 `zf_device_wifi_spi.h` 的 `WIFI_SPI_TARGET_IP`；④ 逐飞助手选 TCP Server、端口 8086；⑤ `CAR_USE_WIFI_LINK` 改 1 | 很值：能直接看到边线和中线对不对 |
| 速度闭环（电池掉了速度也不掉） | `CAR_ENABLE_ENCODER` 改 1；编码器已经修好、方向也确认过了 | 值：但要重新调 `CAR_SPEED_FF/KP/KI`，先用台架命令 `t`（车轮架空）试 |
| 台架调速度环 | 车轮**架空**，发 `t` → 闭环跑 5 秒后回 3 行 `SPD5s`（avg/min/max/cnt/duty）；`[` `]` 改目标速度 ±10 | 值：不用摄像头、不用赛道就能把 PI 调稳 |
| 精确的每米计数 | 第 4 步（推车标定） | 只影响 cm/s 这个单位准不准，不影响跑完一圈 |

### 第 4 步：标定编码器

```c
#define CAR_ENABLE_ENCODER (1)
```

**第一步：先确认读数干净**（用无线串口的 `c` 命令做 **5 秒**采集，命令表见第 10 节）：

1. 无线串口发 **`a`**（切到正交模式），`?` 应该回 `mode=0`；
2. 发 **`c`**，会回一行 `WV: OUTPUT HARD-OFF, collecting 5s -- push the car 1.00 m FORWARD now ...`
   （顺便把电机输出硬关了，轮子自由）；
3. 立刻**用手推着车往前走 1 米**——两个轮子一起连续往前滚，**别来回搓、别只转一个轮子**；
4. 5 秒后回一行（下面这行是 2026-09-20 实测到的真数据）：

```
SUM5s(raw/10): net L=1574 R=1501  abs L=1583 R=1510  flips L=1 R=1  (mode=0 socket=0)
```

判读（`net` = 净计数/10，`abs` = 绝对值之和/10，`flips` = 符号翻转次数）：

| 现象 | 含义 |
|---|---|
| `net` 和 `abs` 差不多（1574 / 1583），`flips` 0~2 | ✅ **干净**：编码器、线、插座都没问题（本车 2026-09-20 实测就是这一行） |
| `net` 远小于 `abs`（60 / 1630），`flips` 几十上百 | ❌ 读数在乱翻：正交模式下不该这样，见第 10 节 |
| 某一侧 `abs` 一直是 0 | 那一侧编码器线没接好 / 插错插座 / `CAR_SWAP_ENCODER_LR` 该改 |
| 推车前进时 `net` 是负数 | 那一侧 `CAR_ENC_x_INVERT` 改成 1（前进应该读正数）。**本车已实测：两边前进都是正数，所以是 0 / 0** |

**第二步：算每米计数**。5 秒窗口内推 1 米时，净计数 = `net × 10`（显示值除以过 10）：

```c
#define CAR_ENC_COUNTS_PER_METER  (net * 10)   // 例：net=1574 -> 15740；推的不是 1 米就按比例换算
```

> 注意：**正交模式的计数是"脉冲数"的 4 倍**（硬件 4 倍频；我们在 `motor_enc_read_pwm()` 里故意
> 不做 4 分频，把低速分辨率留给你）。用 `a` / `d` 换过模式之后这个系数会变，**要重新标一次**。
> 这个值只影响"cm/s 这个单位准不准"。填得不准车也能跑，只是串口显示的速度和目标速度对不上、前馈偏弱。

### 第 5 步：调速度环

```c
#define CAR_SPEED_FF_NUM  (10)   // 先只留前馈：把 KP、KI 都设 0
#define CAR_SPEED_KP_NUM  (0)
#define CAR_SPEED_KI_NUM  (0)
```

跑起来看：车能不能走、速度是不是大致跟着 `spd` 走。然后：

1. 加 `CAR_SPEED_KP_NUM`（先 3 → 6 → 10），直到实测速度和目标接近、且不抖。
2. 还差一点稳态误差，再加 `CAR_SPEED_KI_NUM = 1`。抖了就退回 0。
3. 起步肉/窜：调 `CAR_MOTOR_RAMP_STEP`（大=更猛）；小占空比不转：填 `CAR_MOTOR_DEADZONE`。

### 第 6 步：上赛道调打角与速度

先慢后快：把 `CAR_SPEED_BASE_CM_S` 从 60 开始，一次加 10。

## 6. 症状 → 对策

| 现象 | 原因 / 对策 |
|---|---|
| **直道上车一直往一边跑（往左或往右，图像里线却是直的）** | **fw24 直行微调**：先发 `?` 看 `off=`，再看实时行的 `aim=` 和 `e=近/中/远`。若 `aim`/`e` 基本是 0 → 是**打角零点**偏了（舵机中位机械不正），边跑边按 **`;`（前轮往左 0.5°，车往右偏就按它）** 或 **`'`（往右 0.5°，车往左偏就按它）**，粗调用 `{` / `}`（±2°），直到不跑偏；若 `e` 稳定是 +8/+8/+8 这种固定值 → 视觉中线本身有固定偏差，同样用 `off` 修掉。最后把 `?` 里的 `off=` ÷10 填进 `CAR_SERVO_OFF_DEG` 固定下来。详见下面 fw21~fw27 那一节 |
| 静止时看着前轮就不在正中（歪向一边） | 就是 `off` 要修的东西。上电后**先别发 `o`**（电机不转），往前轮该去的方向按键（歪右就按 `;` 往左修，歪左就按 `'` 往右修），前轮会一点点挪，挪到正中为止 |
| **车在直道上越跑越偏、直接冲出赛道**（不是慢慢偏，是越修越偏） | 打角方向反了（变成正反馈）：发 `n` 在线取反试一把。好了就说明 `CAR_STEER_INVERT` 应该改成 1，把这行结论填回配置 |
| **数据整片不动**（`aim`/`e`/`ang` 一串数值完全不变，只有 `frm` 在涨） | 被"视觉心跳看门狗"锁死了：看 `ST` 行的 `flt`（≠0 就是锁死），舵机会被按在中位不动 —— 这时看到的"往一边偏"其实是中位偏，不是控制算出来的。**发 `o` 解除**（无线串口也会主动喊一行 `WV FAULT`） |
| 该往左打却往右打 | `CAR_SERVO_INVERT` 改 1（发 `k` 自测：`RIGHT +15` 时前轮必须朝右） |
| 直道也左右摆（画龙） | **fw23**：`CAR_STEER_KD` **调小**（在线按 `<`：0.40→0.35→0.30…）、`CAR_STEER_KP` 调小（按 `(`）、`CAR_STEER_D_FILTER` 调到 0.2；还摆就降 `CAR_SPEED_BASE_CM_S`。注意方向别搞反：**画龙是微分太大，不是太小** |
| 入弯切内 / 弯道跟不上 | `CAR_STEER_KP` 加大、`CAR_W_FAR` 加大（提前打角）、`CAR_SPEED_BASE_CM_S` 降低 |
| 出弯过冲、来回摆 | `CAR_STEER_KD` 加大、`CAR_SPEED_CURVE_K` 加大（入弯先减速） |
| 右转时车头甩不过去 | 差速反了：`CAR_DIFF_K` 取负；或左右电机/编码器左右对调 |
| 十字区域乱打角 | 十字时本工程让中线取画面中心（直行）并压速；若仍乱，降低 `CAR_SPEED_CROSS_CM_S`，或加大 `CAR_OPEN_AS_LOST_FRAMES`（让"宽视野"更快被当成十字而不是丢线） |
| 一丢线就冲出去 | `CAR_LOST_STEER_HOLD` 调大（0.8~0.9）、降低 `CAR_SPEED_LOST_CM_S` |
| 串口反复打印 FAULT | 帧率太低导致心跳超时：把 `CAR_TELEMETRY_EVERY` 调大、`CAR_DEBUG_PRINT` 关掉或调大打印间隔；仍超时就加大 `CAR_FRAME_TIMEOUT_MS` |
| 车不动、`dutyL/dutyR` 一直是 0 | 没起步（等按键/延时）、或已 FAULT 锁死（复位）、或 `CAR_ENABLE_MOTOR=0` |
| 低速抖/嗡嗡响不转 | `CAR_MOTOR_DEADZONE` 没填或填小了 |
| 舵机完全不动 | 舵机口选错了（见第 3 节的 10 秒确认法）；或 `CAR_ENABLE_SERVO=0`；或舵机供电不足（要 5V 以上，不能用杜邦线供电） |
| 打印 `LEFT wheel forward` 时，动的却是车右侧那个轮子 | 左右接线反了（**不是**方向问题）：`CAR_SWAP_MOTOR_LR` 置 1。改 `CAR_MOTOR_x_INVERT` 永远改不了"哪一侧" |
| 自检里只转左轮，`encR` 却在变；或只转右轮却动 `encL` | 编码器左右也反了：`CAR_SWAP_ENCODER_LR` 改一下（默认跟电机一起对调） |

## 7. 安全机制（都做好了，不用你管）

1. **上电静止**：DIR 先拉高、PWM 占空比 0，初始化过程电机不会动。
2. **起步门**：延时或按键之后才允许输出（`motor_run(1)`）。
3. **输出斜坡**：占空比每个 10ms 最多变 2%，不会一窜一窜，也保护齿轮箱。
4. **视觉心跳看门狗**：图像超过 `CAR_FRAME_TIMEOUT_MS` 没更新 → 停车并**锁死**（要复位才能再跑，不会自己突然复活冲出去）。
5. **丢线保护**：连续丢线超过阈值停车；丢线时保持打角并降速爬行。
6. **物理限幅**：`CAR_MOTOR_DUTY_MAX` 限制最高车速；`CAR_STEER_MAX_DEG` 限制打角。
7. **左右不交叉**：打角限幅 + 差速下限 0，车不会靠差速在原地打转（速度为 0 时两轮都给 0）。
8. **急停**：任何时候按核心板复位键，电机立刻断输出。
9. **编码器 / 堵转保护**：给着 >15% 的占空比、却连续 500ms 一个编码器计数都读不到 → 判定编码器没接好或轮子卡死，**立刻停车锁死并打印 FAULT**。这条很关键：没有它的话，编码器一断速度环就会一路把占空比加到上限，车直接窜出去。台架自检时这条保护会自动临时关闭。

## 10. 编码器读数乱翻的根因与修复（fw13，2026-09-20）

### 现象

- 台架测试（电机硬关、用手转轮子）时，`SUM2s`（fw14 起叫 `SUM5s`）回的是
  `net L=-60 R=-70  abs L=1630 R=1562  flips L=94 R=104`：
  **净和几乎为 0，绝对值之和却很大，符号在 200 个采样里翻了近百次**。
- 两种模式都这样：`mode=1`（带方向）每 10ms 约 ±15~33，`mode=0`（正交）约 ±73~149。
- `rawL` / `rawR` 的对应关系是对的（只转右轮时只有 `rawR` 动），说明插座、线、`CAR_SWAP_ENCODER_LR` 都没错。

### 根因：库 `zf_driver_encoder.c` 里的一张 static 表

`encoder_get_count()` 靠一张 `static uint8 encoder_dir_pin[]` 判断"这一路当正交还是当带方向"：

| 表里存的东西 | 库怎么处理 |
|---|---|
| `0xFF`（从没被写过） | 当**正交**：`ret >>= 2`（4 分频） |
| 某个引脚号 | 当**带方向**：用那个引脚的**瞬时电平**翻正负 |

而 `encoder_quad_init()` **只配置寄存器，不会把这张表清回 `0xFF`**（只有 `encoder_dir_init()` 会写这张表）。
于是"先按带方向初始化（`CAR_ENCODER_MODE=1` 或开机默认）→ 再用 `a` 切成正交"时：

1. 表里还留着上次写进去的引脚（P42 / P62），库就把正交计数**当成带方向**处理；
2. 正交模式下计数器本来就是**硬件加减计数**、符号已经对了，库却又按 B 相的瞬时电平翻了一次符号。
   A/B 编码器的 B 相是 90° 方波 → **符号随机翻转** → `net≈0`、`abs` 很大、`flips` 一堆；
3. 同时少做一次 `>>2` → **数值偏大 4 倍**（正好解释 mode=0 比 mode=1 大 4~5 倍）。

顺带说明"带方向模式"为什么也不对：把 A/B 编码器的 B 相当 DIR 电平用，一半时间读到低电平，
所以 `mode=1` 时符号照样乱翻。**这恰好就是"这两个编码器是 A/B 型、不是带方向型"的判据。**

### 修复（fw13 + fw14）

| 文件 | 改动 |
|---|---|
| `car_motor.c` | 新增 `motor_enc_read_pwm()` / `motor_enc_read_one()`：**自己读计数器寄存器**（`PWMX_CNTR_ADDR`，高低字节连读两遍核对，避免进位瞬间读到中间值），按**我们自己的模式变量**决定要不要取方向、要不要 4 分频——和初始化顺序、切换历史完全无关。速度环中断改用它们；`encoder_clear_count()` 照旧（它只写计数器，跟那张表无关）。正交模式**有意不做 >>2**，把 4 倍分辨率留给低速 |
| `car_config.h` | `CAR_ENCODER_MODE` 改 **0**；`CAR_FW_TAG` → `fw13`；新增 `CAR_VISION_TRY_MAX`（视觉链路重试上限） |
| `car_control.c` | 汇总行缓冲区 `char buf[96]` → **128**（`SUM5s` 那行最长可能到 115 字符，96 会写穿数组踩栈）；台架自检期间也调 `car_wireless_poll()`，上电就有数据 |
| `car_control.c`（fw14） | 采集窗口 2 秒 → **5 秒**（`CAR_WL_COLLECT_TICKS = 500`），汇总行标签 `SUM2s` → `SUM5s`：推车 1 米用手推 2 秒太赶，标定容易不准 |

| `main.c` | WiFi / TCP / 摄像头三步的 `while(失败){等100ms}` 死循环改成**最多 `CAR_VISION_TRY_MAX` 次**（约 6 秒），超了就跳过视觉链路进主循环——再也不会出现"卡在 WiFi 那一步、串口助手一片空白"。**视觉算法一行没动** |

| 字段 | 含义 / 怎么用 |
|---|---|
| `frm` | 视觉帧计数。**每 500ms 正常涨 20~30**（50fps 左右）；不涨 = 视觉没出数；**只涨 1~2 = 主循环被拖慢了**（图像上传卡住），这时把 `CAR_TELEMETRY_EVERY` 调大或干脆不看图像 |
| `aim` | 加权后的瞄点误差（像素）：**正 = 中线在画面右侧 = 车偏左，要往右打** |
| `e=近/中/远` | 三行各自的**中线偏移**（像素）。判断"视觉中线是不是偏的"就看它：车正对赛道、图像里线是直的，这三个数应该都在 0 附近；若稳定是 +8/+8/+8，说明有固定偏差 → 正好用 `off` 修 |
| `lost=左/右` | 视觉组数出来的、整幅图里左 / 右线各丢了多少行（fw30 起）。**直道上应该只有 0~几行**；几十行说明那条线大段是补出来的。注意：**弯道里外侧丢几十行是正常的**（线跑出画面了） |
| `dutyL` / `dutyR` | 左右轮占空比（万分比）。直道上两个数应该一样；差很多 = 差速或某一侧电机不对。`duty=0` 时先看 `ST` 行的 `flt` |
| `spdL` / `spdR` | 实测速度（`CAR_ENABLE_ENCODER = 0` 时一直是 0） |

**第 4/5/6 行 `PF1` / `PF2` / `PF3`（fw36 起，每 `CAR_PERF_EVERY × CAR_WL_PERIOD_MS` = 2 秒三行：一帧的时间到底花在哪）**

```
ST st=1 flt=0 out=0 dt=20ms off=-25 steer=-38 ang=1013 v=38 w=83/71/81
EN encL=0 encR=0 rawL=0 rawR=0 invL=0 invR=0 mode=0 socket=0
CT frm=1089 aim=-8 e=-2/-2/-14 lost=28/32 dutyL=0 dutyR=0 spdL=0 spdR=0
PF1 n=84 dt=240 fps=41 wt=10 pl=0 al=213 (0.1ms)
PF2 cp=33 vs=179 ct=1 osc=0 img=18 mx=600 slow=0
PF3 mxc=100 mxv=200 mxk=100 mxi=100 mxw=300 mxo=0 (0.1ms)
```

**所有时间都是 0.1ms 单位**：`dt=240` 就是 **24.0ms**（÷10 = ms；10000 ÷ dt = fps）。上面这组是 fw37 在车上实测到的数。

> fw35 那一版这里的换算写错了一档（打出来其实是 ms），所以当时看到的 `dt=71` **本来就是 71ms**；fw36 修正后同一个数会显示成 `dt=710`。两行是同一个东西，别混。

| 字段 | 含义 / 怎么用 |
|---|---|
| `n` | 这 2 秒里统计到多少帧（≈ 循环帧率 × 2）。`n=0` = 一帧都没进来（视觉停了，或者 `DEBUG_SKIP_ALGORITHM = 1`） |
| `dt` | **平均帧间隔 = 控制周期**。`dt=240` → 24ms → **42fps**。**和助手右上角的 FPS 对一下：助手显示的是发图速率 = 这个帧率 ÷ `CAR_TELEMETRY_EVERY`（3）→ 42fps 在助手上只有 14fps，"个位数帧率"是这么来的** |
| `fps` | （fw38）**主循环真实帧率 = 10000 ÷ `dt`**。**这才是车实际拿到的帧率**（车是每一帧都在控制、每一帧都拿到新中线）；助手右上角那个 FPS 是**发图速率**，只代表"每几帧往电脑传一张图"，别再被它误导 |
| `wt` | 其中**空转等摄像头**占多少。它大 = 帧率被摄像头/曝光限制；**它很小 = 摄像头出帧比我们处理得还快，瓶颈在我们自己这边** |
| `pl` | 无线串口轮询 + 定时上报（`sprintf` + 串口发送）占多少。几毫秒正常；大了按 `--` 把上报周期从 500ms 拉长 |
| `al` | **算法总时间 = `cp + vs + ct`**（放这一项是为了和 fw35 的 `al` 直接对比） |
| `cp` | **灰度快照**（`image_gray_copy`，含阈值计算）—— 防图像撕裂必须做的那张快照 |
| `vs` | **视觉算法**（寻线 / 十字 / 圆环 / 平滑 / 贴边）—— 视觉组的代码，我们一个字不碰 |
| `ct` | **整车控制** `car_control_update()`（读三行中线 → PD → 舵机 + 速度）—— 我们自己的代码 |
| `osc` | 逐飞助手示波器发送占多少。`CAR_USE_WIFI_LINK = 0` 时应该是 0（fw35 起才真的做到） |
| `img` | 图像上传占多少。每 `CAR_TELEMETRY_EVERY` 帧才发一次，所以平均值 ≈ 单次发图耗时 ÷ 3 |
| `mx` | 窗口里**最大**的帧间隔（同样 0.1ms：`mx=1000` = 100ms）。明显比 `dt` 大、或者 `slow > 0` = 中间"偶尔卡一下"（网络 / 模块 / 上位机） |
| `slow` | 窗口里超过 100ms 的帧数 |
| `PF3` 的 `mxc / mxv / mxk / mxi / mxw / mxo` | **每一段各自的最大值**（同样 0.1ms）：平均值看不出"偶尔卡一下"，这一行能。**谁大就是谁卡**：`mxk` 大 = 卡在整车控制里（fw37 之前正是这个：USB 调试 `printf` 每 50 帧卡 350ms → `mxk=3500`）、`mxi` 大 = 卡在发图、`mxv` 大 = 算法里有慢帧 |

**按 `PF1` / `PF2` 定位"帧率上不去"**：

| 看到的现象 | 结论 / 下一步 |
|---|---|
| `wt` 占了一大半 | **摄像头出帧慢**：试 `CAMERA_LOW_FPS_ENABLE = 1` + `CAMERA_LOW_FPS_VALUE = 50` 看 `wt` 掉不掉；掉不动说明是曝光 `MT9V03X_EXP_TIME_DEF(512)` 把帧率压住了 |
| `wt` 很小、`vs` 占了一大半 | **视觉算法本身慢** —— 2026-09-23 台架实测就是这种（`dt=710 wt=30 cp≈180 vs≈430 ct≈50`）。我们能做的只有"打开编译器优化"（fw36 已做）或请视觉组优化算法 |
| `cp` 大 | 灰度快照慢：这是防撕裂必须做的；唯一能省的办法是把摄像头帧率也降下来 |
| `ct` 大 | 我们自己的控制慢：查 `car_control_update()`（正常只有几毫秒） |
| `img` 大 | 发图太频繁：`CAR_TELEMETRY_EVERY` 调大（3 → 6），或者 `CAR_USE_WIFI_LINK = 0` 完全不发 |
| `mx` / `slow` 大，同时某一段的 `mx?` 特别大 | **某一段里偶尔卡了几百毫秒**：看 `PF3` 指的是哪一段 —— `mxk` 大 = 我们控制里的阻塞调用（USB `printf`、`system_delay_ms` 之类），`mxi` 大 = 发图链路，`mxv` 大 = 算法里有慢帧 |
| `pl` 大 | 上报太频繁：按 `--` 把上报周期拉长 |
| `n` 个位数、`dt` 上千 | 链路半死：fw34 的自动停发会救回来（串口会喊 `WV WARN: wifi link stalled`），先把上位机 / 热点弄通 |

> **提醒**：各段都是用 10ms 计数器在帧内取的差值，**单帧只可能是 0 或 10 的倍数**；`PF1/PF2` 报的是 2 秒窗口（几十帧）的平均值，够用。想看更细就把 `CAR_PERF_EVERY` 调大（窗口更长、平均更准、刷新更慢）。

### fw36：把"帧率卡在哪"量出来 + 打开编译器优化（Level 8）

**实测（2026-09-23 台架，fw35，`out=0` 电机不转）**：

```
ST st=1 flt=0 out=0 dt=60ms off=-25 steer=-37 ang=1012 v=40 w=82/65/59
CT frm=193 aim=-7 e=-10/-6/-8 lost=25/27 dutyL=0 dutyR=0 spdL=0 spdR=0
PF n=30 dt=71 wt=3 pl=0 al=66 osc=0 img=2      (fw35 那一版的单位是 ms)
```

**结论**：

1. **`wt=3ms`：空转等摄像头只花 3ms** —— 摄像头出帧比我们处理得还快，**帧率完全是自己算得慢**，跟摄像头 / 曝光 / WiFi 都无关（`osc=0`、`img=2` 也说明链路一点没拖后腿）。
2. **`al=66ms` 就是主循环的全部时间**：`wt+pl+al+osc+img = 3+0+66+0+2 = 71 = dt`，账刚好对上（说明这套计时是可信的）。
3. 所以 66ms 里"快照 / 视觉算法 / 我们自己的控制"各占多少必须量出来 —— fw36 把 `al` 拆成 `cp` / `vs` / `ct`。
4. **顺手发现一个大问题**：Keil 工程里 C251 的**优化等级一直是 `Level 0`（完全不优化）**，逐飞所有例程都是这个值，谁都没动过。用**同一份源码**在 `_opt_build` 里对比编译：

   | 优化等级 | code 大小 | 结果 |
   |---|---|---|
   | `Level 0`（原来） | **156672 字节** | 0 Error / 0 Warning |
   | `Level 8`（fw36 起） | **108493 字节** | 0 Error / 25 Warning（全是"条件恒假 / 初值被覆盖"这类无害告警） |

   代码小了 **31%**，对这种逐像素的视觉算法通常意味着接近翻倍的速度，所以 fw36 把优化等级改成 8。

**fw36 改了什么**：

| 改动 | 说明 |
|---|---|
| `PF` 拆成 `PF1` / `PF2` | `PF1` = `n dt wt pl al`；`PF2` = `cp vs ct osc img mx slow`（`al = cp + vs + ct`） |
| **修正单位换算** | fw35 的 `×10` 算出来是 ms；现在 `×100` 才是真正的 0.1ms（`dt=710` = 71.0ms） |
| **C251 优化等级 0 → 8** | Keil：`Options for Target` → `C251` 标签 → `Optimization` 选 `Level 8`。**★你那份 Keil 工程如果是改之前打开的，内存里还是 Level 0**：要么在 Options 里手动改成 8，要么把工程关掉重开。编译完看 Build Output 的 `code=`：**108xxx 才是优化生效，15xxxx 说明还是 Level 0** |
| `soft_delay()` 加 `volatile` | 优化一开，编译器会把"空循环延时"整段删掉，而 `soft_delay()` 正好用在 **PLL 时钟启动**那段（等锁相环稳定）。它的局部变量原来没有 `volatile`，在 Level 0 下侥幸能用；不改的话 Level 8 会把延时删掉 → 时钟可能不稳。改的是 `libraries/zf_driver/zf_driver_delay.c` 一行 |
| `main.c` 删掉一个没用的中间变量 | `inside_ticks` 原来算了没用上，开优化后编译器立刻报"死赋值"，顺手改成真正用它 |

**开优化前的安全性核对**（都查过）：
- 我们自己的中断共享变量（`motor_tick_cnt` / `motor_duty_*` / `motor_speed_*` / `motor_enc_*` …）**全部带 `volatile`** ✓；
- 库里的延时：`system_delay()` 用**硬件定时器 T11** ✓，`soft_iic_delay()` / `func_soft_delay()` 都带 `volatile` ✓，只有 `soft_delay()` 有问题（已修）；
- 25 条告警逐条看过：全是"配置宏恒假 → 分支不可达"（例如 `if(0 != CAR_MOTOR_L_INVERT)`）和"变量初值随后被覆盖"，**没有一条是硬件寄存器写被删掉**。

### fw37：关掉阻塞的 USB 调试打印（又把控制周期砍掉一大块）

**fw36 实测（Level 8 之后，台架，`out=0`）**：

```
ST st=1 flt=0 out=0 dt=20ms off=-25 steer=0 ang=975 v=0 w=0/0/0
CT frm=1424 aim=4 e=0/0/0 lost=1/1 dutyL=0 dutyR=0 spdL=0 spdR=0
PF1 n=99 dt=257 wt=7 pl=0 al=219 (0.1ms)
PF2 cp=38 vs=112 ct=69 osc=0 img=30 mx=3600 slow=3
```

**先说好消息**：`dt` 从 **71ms → 25.7ms**（14fps → **39fps**，`ST` 行的瞬时 `dt` 甚至已经到 20ms = 50fps）。光把 C251 优化等级从 `Level 0` 改成 `Level 8` 就快了 **2.8 倍**，算法一个字没动。

**但 `ct=6.9ms` 说不通** —— `car_control_update()` 只有几十条浮点运算，不可能要 7ms。再看 `mx=3600`（有一帧 360ms）、`slow=3`（3 帧超过 100ms），一算就明白了：

```
car_control_update() 末尾"每 50 帧打印一行"的 printf 走的是 USB CDC，
USB 打印是【阻塞】的（要等主机来取数据），实测一次卡 ~340ms：
    2 次 × 340ms ÷ 99 帧 = 6.9ms/帧        ← 和 PF2 的 ct=69 完全对上
```

**这就是 fw37 修的东西**：

| 改动 | 说明 |
|---|---|
| `CAR_PRINT_EVERY_FRAMES` 50 → **0**（0 = 关掉） | 那句 USB 调试打印不再执行。要看这行信息就把值改回 50（帧率会掉几帧，属正常） |
| `IMAGE_THRESHOLD_PRINT_FRAME` 50 → **0** | 视觉组那句"每隔 50 帧打印阈值"也是同样的 USB 阻塞打印，一起关掉（要诊断阈值再改回 50） |
| 代码里加 `(0 != CAR_PRINT_EVERY_FRAMES)` 判断 | 这样配置写 0 才是"关掉"，而不是变成"每帧都打印" |
| 新增 **`PF3` 行** | 打印**每一段各自的最大值**（`mxc mxv mxk mxi mxw mxo`）：平均值看不出"偶尔卡一下"，这一行直接指出是哪一段 —— 这次就是 `mxk=3500`（卡在控制里） |

> **教训（后面写代码都按这条来）**：跑车主循环里**任何** USB `printf` 都是定时炸弹 —— 它阻塞、而且跟帧率无关地随机卡几百毫秒。要打印就用**无线串口**（UART8，走 FIFO 不阻塞），我们那 5 行上报就是这么做的（`pl=0ms` 就是证据）。

**fw37 实测验证（2026-09-23，车上，视野里有赛道）**：

```
PF1 n=84 dt=240 wt=10 pl=0 al=213 (0.1ms)
PF2 cp=33 vs=179 ct=1 osc=0 img=18 mx=600 slow=0
PF3 mxc=100 mxv=200 mxk=100 mxi=100 mxw=300 mxo=0 (0.1ms)
```

| 项 | fw36 | fw37 | 结论 |
|---|---|---|---|
| `ct`（整车控制） | 6.9ms | **0.1ms** | USB `printf` 就是元凶，改完立刻归零 ✓ |
| `slow`（>100ms 的帧数） | 3 | **0** | 350ms 冻结彻底消失 ✓ |
| `mx`（最大帧间隔） | 360ms | **60ms** | 同上 ✓ |
| `dt` | 25.7ms | **24.0ms** | 这次循环 = **42fps** |
| `vs`（视觉算法） | 11.2ms | 17.9ms | **不是变慢了，是场景变了**：台架那次视野里什么都没有（`lost=1/1 w=0/0/0`），这次是赛道（`lost=28~33 w=83/71/81`），算法要多做补线 / 十字 / 圆环判断 |

**42fps 时的时间构成（ms）**：`vs 17.9`（视觉算法，占 **75%**）+ `cp 3.3`（快照）+ `img 1.8`（发图）+ `wt 1.0`（等摄像头）+ `ct 0.1`（我们的控制）—— **我们自己的开销一共只有约 5ms**，剩下全是视觉组的算法。

**还量到一个信息**：`mxw=300`（有一次等摄像头等了 30ms）说明**摄像头自己的出帧周期约 20~24ms（≈45fps）** —— 我们现在的 42fps 已经跑到摄像头速度的 ~90%。也就是说，**当前曝光（`MT9V03X_EXP_TIME_DEF = 512`）下即使算法再快一倍，也就 45fps 左右**；想再往上必须先降曝光（图像会变暗，阈值要跟着调）。

> ⚠️ **帧率涨了 3 倍之后，打角参数可能要跟着动**：`s_d_aim_filt` 的一阶低通（`CAR_STEER_D_FILTER = 0.35`）是**按帧**滤波的，帧率变 3 倍等于它的时间常数缩到 1/3 → 视觉噪声更容易串进微分项。**如果直道上开始画龙/发抖，先按 `<` 把 `KD` 降下来**（每次 −0.05），或者把 `CAR_STEER_D_FILTER` 从 0.35 调到 0.15。

### fw47：圆环行驶 **v2** —— 先直行过第一个路口，到第二个路口才打角

**用户的原话**（附赛道照片，红线画的是要走的路径：沿直道一直往上开，**过了下面那个口子**才往右拐进环）：

**先说结论：识别 ≠ 进环时机。** 视觉组那套判据（`ring_road.c`："一边张开 + 对面是连续直道"）是**识别**用的，它认出来的是"这里有环"；而**从哪儿拐进去**是另一件事 —— 入口那一侧有**两处张开**（= 开口的两个拐点）：

| 位置 | 视觉组叫什么 | 图像里的样子 | 车该干什么 |
|---|---|---|---|
| **第一个路口**（近端拐点） | `ring_open_row1` / `ring_corner_row` | 入口侧边线**开始**断掉（道路开始变宽） | **不进**，继续直行 |
| 开口中间 | `track_lost[]` 入口侧那一大段丢线（实测 50~60 行） | 那一侧整片是白的，对面那条边还是直的 | **直行**通过 |
| **第二个路口**（远端拐点） | `ring_open_row2` | 入口侧边线**恢复**（开口走到车头/出画面） | **在这里打角进环** |

### fw47b：圆环**可信度闸门** —— 治"看到什么都觉得是圆环"

**为什么会"到处都是圆环"**：视觉组的识别判据（`code\ring_road.c`）是「**入口侧连续丢线 ≥ 25 行** 且 **对面那条边是直道**」，而**弯道里外侧边线跑出画面**恰好也是这个特征（他们自己的文档里也写了"大弯道边线跑出画面是物理限制"）—— 所以只要有一侧的线成片丢掉，圆环就"到处都是"。剩下的常见来源：**二值化/场地灯光**把某一侧的线整段吃掉（`lost` 行数一下几十行），一样能骗过判据。

**对策：闸门**（`s_rp_gate_on`，**在线按 `s` 循环切 0 / 1 / 2**，默认 **2 = 最严**）：

| 档 | 要求 |
|---|---|
| `0` | 关（老行为：报了就当圆环） |
| `1` | ① 识别那一刻**在直道上**（`curve ≤ CAR_RING_GATE_CURVE_MAX` 20 —— 圆环都是从直道进的，弯道里报的先不信）②**开口有界**（开口远端还得能看到 ≥ `CAR_RING_GATE_MIN_ABOVE`(12) 行边线 = "第二个路口看得见"；外侧线跑出画面时丢线会一直顶到画面最上面，这条过不了）③ 开口够长（`≥ CAR_RING_GATE_MIN_OPEN` 20 行） |
| `2` | 再加 ④ **视觉组自己看到"环内特征"了**（`ring_white_row` 全白行 / `ring_trans_row` 黑白跳变行，也就是他们方法二的判据）才允许打角进环 |

闸门不过 = **当没看见**：不锁瞄点、不打角（视觉组的补线我们管不了，但至少**不跟着它冲**）。另外直行阶段还有一道兜底：**弯道程度连续 `CAR_RING_ABORT_N`(6) 帧超 `CAR_RING_ABORT_CURVE`(45)** 就判定是误判，**立刻放开瞄点**（防止"误报 + 锁瞄点"把车带进沟里）。

### fw49：**看到弯道就开始减速**（提前量）

原来只有 `curve = |远端偏移 − 中间偏移| × 2` 这一项，它要等弯道**进到中/远行之间**才涨起来 —— 也就是车头快进弯了才开始减速，实车感觉"看见弯了但来不及"。

现在加一项**提前量**（`car_control.c` 的 4.7 段）：

```
speed = 基准 − 弯道系数 × 弯道程度 − 提前系数 × (|远端偏移| − 死区)
                                 ↑ 新增：远端行(58)看的是最前面那一段，前面一有弯它先偏
```

| 参数 | 默认 | 在线键 | 说明 |
|---|---|---|---|
| `CAR_CURVE_EARLY_K` | **0.25** | **`7` / `8`** ∓0.05 | 提前减速系数（`?` 里看 `evk`，×100；0 = 关掉提前量） |
| `CAR_CURVE_EARLY_DEAD` | **6** 像素 | — | 死区：远端偏移小于它不动，挡直道上的几像素抖动 |

直道上 PID 把 `aim` 压在 0 附近、远端偏移只有几像素 → 死区挡掉，**不会平白无故慢下来**；一有弯远端先偏出去 → 立刻开始减速，弯越近偏得越多、减得越狠。原来那项 `CAR_SPEED_CURVE_K`（`5`/`6` 调）继续管"弯里减多少"，两项叠加。

> 另外把 `圆环识别逻辑.md` 单独写成一份（见工程根目录），从 `main.c` 的每帧调用顺序、视觉组四条判据、状态机、两个路口、补线、侧别判定的漏洞，一直写到我们加的三道防线、全部参数表、诊断字段和"现象→处理"对照表 —— 方便直接发给视觉组。

### fw47d：弯道里**不叫**圆环模块 + 入口侧**标签纠错**

**① 弯道里直接不调用 `ring_road_process()`**（`main.c`，闸门档位 ≥1 时生效）

**② 入口侧"标签纠错"**（`ring_type` 被他们判反时我们直接改回来）

**诊断顺序**（车"到处报圆环"时）：
1. 发 `?`，看 `gfail` 涨不涨：**涨** = 闸门正在挡它，说明挡对了（车没跟着冲）；**一直是 0 但 `ring=1/2`** = 闸门放行了，那就把 `orow` / `owhite` / `cv` 发我，看是判据太松还是二值化丢线；

3. 只有在**弯道里**才报 → 说明是"外侧线跑出画面"骗过判据，闸门档 1/2 应该已经挡住；还漏就把 `CAR_RING_GATE_CURVE_MAX` 调小（比如 12）；
