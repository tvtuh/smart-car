# 种子生长法寻线说明

> ## 丢线贴边（`track_pin_lost_edges`）
>
> **连续丢线很多行（≥ `TRACK_EDGE_PIN_ROWS`，默认 12），而且丢线前那一段已经贴近画面边缘
> （离边缘 ≤ `TRACK_EDGE_PIN_NEAR`，默认 30 像素）** → 说明这条边线**已经跑出画面**了，
> 这时把整段**直接贴到画面边上**（左线贴第 0 列，右线贴第 187 列）。
>
> 不这样做的话，边线会保持丢线前的值、停在画面中间**"乱飘"**，看起来就是歪的。
>
> **为什么要加"贴近边缘"这个前提**：十字和圆环也会产生长丢线段，但那些丢线段的端点
> 在画面中间（横杠边缘、环岛边缘），**不能贴边**。加了前提之后实测：
> - 十字：**0 行**被贴边 ✓（不会误伤）
> - 大弯道 curv=40：68% 的丢线行被贴边；curv=60：**94%** ✓
>
> 调用位置在 `track_line_smooth()` **之后**（先让插值把边线弄平滑，再覆盖那些确实出画面的段）。

参考文章：[智能车图像处理(二)基础寻线](https://blog.csdn.net/weixin_50567482/article/details/119353098)

## 一、先说清楚：文章里没有种子生长法的代码

文章把巡线分成三类：

1. **基础扫线**：由中线分别往左右两边扫，找黑白跳变点（文章给了完整代码）
2. **上一行引导的局部搜索**：先扫最靠近车身的一行确定左右边界，之后每行在上一行边界附近搜索（文章给了完整代码，也是作者比赛实际用的方法）
3. **种子生长法**：文章**只有文字描述，没有代码**。作者原文写着：
   > "第三种巡线方式之后如果能够写出来，可能会添上。"

文章对它仅有的描述是：

> "以寻到的两个点为基础，框出一个 3×3 的矩形框，分别对左右两个点所在的矩阵框内进行顺时针和逆时针扫描，找到跳变点，依次往下扫描。"

所以 `code/track_edge.c` 是**按这段文字描述实现**的，不是抄文章的代码。

## 二、实现流程

```
1. 起始行(最靠近车身的一行)扫描
   从画面中心向左找 "黑黑白" 跳变 -> 左边界种子
   从画面中心向右找 "白黑黑" 跳变 -> 右边界种子
   （对应文章的 first_scan）

2. 逐行生长
   以上一行的左边界为种子，在种子附近找 "左黑右白" 的跳变点作为本行左边界
   以上一行的右边界为种子，在种子附近找 "左白右黑" 的跳变点作为本行右边界
   找到的点作为下一行的新种子，一行一行往远处推进

3. 中线 = (左边界 + 右边界) / 2
```

## 三、PC 仿真结果：3×3 到底能不能用

我用 PC 仿真把算法原样跑了一遍（188×120，20 次随机测试取平均，统计"丢失行数"和"与真实边界的误差"）。

**理想图像（无噪声）：**

| 赛道 | 算法 | 丢左行 | 丢右行 | 平均误差 |
|---|---|---|---|---|
| 直道 | 固定 3×3 | 0 | 0 | 0.5 px |
| 缓弯 | 固定 3×3 | 0 | **94** | 20.1 px |
| 急弯 | 固定 3×3 | **119** | **115** | 67.6 px |

**加 1~2 像素边界抖动（真实二值化的常态）：**

| 赛道 | 算法 | 丢左行 | 丢右行 | 平均误差 |
|---|---|---|---|---|
| 直道 | 固定 3×3 | 115.8 | 116.5 | 38.4 px |
| 直道 | **逐圈扩大到 ±5** | **0** | **0** | **1.5 px** |
| 缓弯 | 固定 3×3 | 115.8 | 117.7 | 36.7 px |
| 缓弯 | **逐圈扩大到 ±5** | **0** | 39.6 | 6.6 px |
| 急弯 | 固定 3×3 | 118.2 | 115.9 | 67.4 px |
| 急弯 | **逐圈扩大到 ±5** | 15.9 | 68.5 | 13.2 px |

**结论：**

- **3×3（文章的描述）在理想图像上、直道和大半径弯道是能用的**，这也是作者当时"没有继续往下深究"的原因——短时间测试看不出问题；
- 但**二值化边界只要有一两个像素的抖动，3×3 就会大面积跟丢**（119 行丢 115 行），因为真实的赛道边界每行移动经常超过 1 个像素；
- 改成**"先在 3×3 里找，找不到再逐圈扩大到 ±5"**之后，直道完全不丢线（平均误差 1.5 像素），缓弯左线也不丢；
- **急弯仍然是弱点**（右线会丢 60 行左右），要彻底解决得上八邻域/爬线算法或者补线。

## 四、参数

在 `code/track_edge.h` 中：

| 宏 | 默认值 | 说明 |
| --- | --- | --- |
| `TRACK_SEED_BOX` | 5 | 搜索框最大半径。改成 1 就是文章严格的 3×3 |
| `TRACK_RECOVER_LOST` | 5 | 连续丢线多少行后做全局扫描重新捕获边线 |
| `TRACK_MEDIAN_ENABLE` | 1 | 是否做 3 点中值滤波去毛刺 |
| `TRACK_DEBUG_MARK` | 1 | 是否把丢线行画成黑横条（调试用，跑车时可关） |
| `TRACK_SEED_COL` | 94 | 起始行从画面哪一列开始向两边搜索（画面中心） |
| `TRACK_WHITE_LEVEL` | 128 | 二值化图像中 ≥ 本值算赛道（白） |
| `TRACK_START_ROW` | 119 | 起始行（最靠近车身的一行） |
| `TRACK_END_ROW` | 0 | 结束行（最远的一行） |
| `TRACK_ROW_STEP` | -1 | 行推进方向，正装 -1 |

**摄像头安装方向很重要**：哪一行"最靠近车身"取决于摄像头正装还是反装。
正装时画面远端在上，最靠近车身的是最后一行 119；反装时是第 0 行。
反装除了把 `TRACK_START_ROW` 改成 0、`TRACK_ROW_STEP` 改成 +1 之外，
**左右边界数组也要对调**（反装时画面左右是反的）。

## 五、结果显示

`user/main.c` 里 `INCLUDE_BOUNDARY_TYPE` 已经设为 **1**，表示"图像 + 三条边线"，
三条边线直接指向 `track_left` / `track_center` / `track_right`，每帧自动更新：

```c
seekfree_assistant_camera_boundary_config(X_BOUNDARY, MT9V03X_H,
        track_left, track_center, track_right, NULL, NULL, NULL);
```

串口（115200）每 50 帧打印一次状态：

```
th:150 start L:24 R:167 lost L:0 R:3
```

- `th`：当前二值化阈值
- `start L/R`：起始行（最靠近车身）寻到的左右边界列坐标
- `lost L/R`：整幅图左右边线各丢失多少行，**正常情况下应该是 0 或者个位数**

如果 `lost` 很大或者 `start L/R` 明显不对，说明二值化阈值不对或者赛道不在画面中心。

## 六、边线后处理（丢线行插值 + 去毛刺）

寻线在丢线时是"保持上一行的值"，画出来就是**一截竖线，而且上下两端还接不上**，
所以整体看上去歪歪扭扭。`track_line_smooth()` 负责收尾，调用顺序：

```c
track_edge_process(image_copy[0]);      // 寻线
cross_road_process(image_copy[0]);      // 十字补线（靠原始丢线标志决定补哪些行）
track_line_smooth();                    // 丢线行插值 + 3 点中值滤波 + 重算中线
```

| 步骤 | 做什么 | 开关 |
| --- | --- | --- |
| 丢线行插值 | 每一段连续丢线的行，用它上下两端的有效边线值线性插值补上 | 常开 |
| 3 点中值滤波 | 去掉单行的毛刺（文章里也提过"图像锯齿"的问题） | `TRACK_MEDIAN_ENABLE` |

**PC 仿真量化结果**（8 组随机测试，和真实边线比较平均绝对误差，单位像素）：

| 场景 | 原始 | +插值 | +插值+中值 |
| --- | --- | --- | --- |
| 十字（横杠 29~57）全图 | 2.66 | 1.56 | **1.39** |
| 十字（宽横杠 25~80）全图 | 8.02 | 4.91 | **4.79** |
| 直道 全图 | 1.11 | 1.11 | **0.89** |
| **只统计丢线的行**（横杠 29~57） | 7.47 | **2.82** | 2.82 |
| **只统计丢线的行**（宽横杠 25~80） | 15.64 | **8.89** | 8.89 |

丢线行的误差降低 43%~62%，干净的直道不退化（中值滤波还略有改善）。

## 七、实车调优记录

### 1. 跳变判据换成"三像素"（文章本来就用这个）

实车帧里黑区能看到明显的白噪点（固定阈值二值化的散粒噪声）。原来跟线用的是**两像素判据**
（`左边黑 + 当前白`），一个孤立白噪点就能骗出一次假跳变。

改成文章扫线用的**三像素判据**：

- 左边界：`黑 - 黑 - 白`
- 右边界：`白 - 白 - 黑`

PC 仿真（8 组随机测试，与真实边线比较）：

| 散粒噪声 | 判据 | 丢左行 | 左线平均误差 | 中线平均误差 |
| --- | --- | --- | --- | --- |
| 0.5% | 两像素 | 5.5 | 1.89 | 2.59 |
| 0.5% | **三像素** | **4.0** | **1.21** | 2.58 |
| 1.0% | 两像素 | 6.0 | 2.38 | 2.67 |
| 1.0% | **三像素** | **4.0** | **1.22** | **2.08** |

并且验证过**不影响十字识别**：正入 8/8、斜入 8/8、直道弯道 0 误报（与两像素判据完全一致）。

### 2. 丢线行可视化（`TRACK_DEBUG_MARK`）

打开后，**左线丢线的行会在边界处画一小段黑横条**，右线同理。
上位机图像上看到黑横条的位置，就是寻线没找到边线的那些行 —— 一眼就能看出是丢在横杠区、
顶部还是某一侧。它是在所有寻线/补线处理之后才画的，**不影响任何计算结果**。
跑车时把 `track_edge.h` 里的 `TRACK_DEBUG_MARK` 改成 0 关掉。

## 八、和文章代码的差异

1. 文章的寻线是**全局扫描**（每行都从头找起），种子生长法是**局部生长**（只在上一个种子附近找），抗干扰更好但跟丢后不容易自己找回来；
2. 文章的 `Follow_scan` 里 `last_left_line` / `last_right_line` 没有在循环里更新（每行都在同一个窗口扫描，只能寻出一条竖线），本实现改成每行都更新种子；
3. 搜索框从固定的 3×3 改成"由小到大逐圈扩大"，原因见第三节的仿真数据。
